| **Diagnosis**   | **Established statically.** The cooldown floor is derived from Groq's `x-ratelimit-remaining-tokens` / `-limit-tokens` / `-reset-tokens` response headers, which `_parse_token_headers` (`llm_caller.py:699`) reads from `_captured_response_headers`. | Field | Detail |
|---|---|
| **Symptom** | Inside the `doc_writer` loop of #9, a message trace showed the model's `file_name` argument mutating across turns: `essay.txt`, then `essay.txt` again, then the full `C:\Users\LOQ\Desktop\Projects\Bhai-To-Bhai\yt-tutorial\temp\essay.txt`. Every call still reported success. |

## 16. A repetition loop inside a grammar-constrained tool argument runs `max_tokens` out mid-string, and the server rejects two minutes of work

| Field | Detail |
|---|---|
| **Symptom** | `openai.UnprocessableEntityError: 422 — Tool error: Failed to parse generated text: EOF while parsing a string at line 1 column 3725`, always **immediately after a writing tool call had succeeded**, always 100–180s later. In `run_logs/agent_run_20260806_133245.debug.log` all three writing-team turns fail this way — `doc_writer` at 102s (422), `note_taker` at 169s (`APITimeoutError`), `doc_writer` again at 171s (deadline). `search` completes in 17–20s every time in the same runs. An earlier instance rejected `invalid escape at line 1 column 2715` instead. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/`, local TGI `3.0.0-sha-8f326c9`, `llama-3.1-8b-instruct`, `temperature=0.1`, `max_tokens=2048`, `frequency_penalty` unset. |
| **Diagnosis** | **Established from the rejected generation, which the 422 body quotes verbatim.** The model was re-emitting the same two URLs over and over with the backslash escaping doubling on each pass (`\\` → `\\\\` → `\\\\\\\\`), until it exhausted `max_tokens` in the middle of the JSON string — which is exactly what "EOF while parsing a string" means. | **Resolution** | **Fixed, at both causes, and the fix is a probability reduction rather than a guarantee.** `LLM_FREQUENCY_PENALTY = 0.4` in `config.py`, applied on the client in `llm/clients.py` for both providers and confirmed on the wire (`{'frequency_penalty': 0.4, 'temperature': 0.1, 'max_completion_tokens': 2048}`); penalising by token count is what breaks a repetition loop, and temperature was deliberately left at 0.1 so supervisor routing keeps its determinism and only one knob moved. The `Sources:` line was removed from `SEARCH_AGENT`'s report format, each URL now cited once on the item it supports, with a BAD example showing the triple-citation case. `tools/documents.py` gained `_unescape()` so the escape damage that does get through never reaches disk (#20). | **Prevention** | Three notes, in increasing generality. A **grammar-constrained decoder removes the loop's own exit**: ordinarily a repeating model eventually emits a stop token, but here the schema forbids it until the string closes, so a soft degeneracy becomes a hard request failure. **A report format is an input format** — `SEARCH_AGENT`'s citation style was written to make findings verifiable and its cost was measured downstream, in a different agent, two turns later; anything one agent's output format repeats is something the next agent's decoder is primed on. And for the orchestrator: **sampling parameters are deployment configuration, not tuning trivia**, in the same category as `STRUCTURED_OUTPUT_METHOD` (#8) — this one is the difference between a working pipeline and a 422 after two minutes of billed generation, and nothing in the calling code would have named it. |

## 17. Two timeouts that structurally could not fire — a per-read socket timeout, and an executor that blocks on the call it is escaping

| Field | Detail |
|---|---|
| **Symptom** | The pipeline hangs with no log line for minutes at a time. `run_logs/agent_run_20260806_131721.debug.log` stops at `create_outline -> outline.txt` at 13:17:53 and produces nothing further for nine minutes. An earlier run recorded `note_taker` running 12:57:08 → 13:03:36 — **388 seconds** — and ending on the server's own HTTP 500, not on any limit of ours. `LLM_RESPONSE_TIMEOUT_SECONDS = 150` was set, live in the running process, and never fired. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/`, `httpx` 0.28.1, `openai` SDK, `langchain-openai` 1.4.1, local TGI. Source mtimes confirmed the running process did carry the 150s setting. |
| **Diagnosis** | **Established, two independent defects with the same consequence.** (a) `LLM_RESPONSE_TIMEOUT_SECONDS` is a **per-read** timeout: httpx restarts the clock on every byte received, so a server that accepts the request and holds the socket open while it generates never trips it, however long it thinks. This is why the 388s turn ended in a 500 rather than an `APITimeoutError` — an isolated test against a server that sends *nothing* raised in exactly 4.0s, confirming the setting works and simply does not measure the right thing. Worse, the setting had not even been reaching worker calls: `create_agent` invokes `model_.invoke()` directly inside LangChain's factory, so workers never pass through `llm/invoker.py`, and `ChatOpenAI` was constructed with no timeout — the effective value was the OpenAI SDK default of `read=600`. (b) The supervisor path's timeout was decorative for a different reason: `_invoke_once` wrapped its call in `with concurrent.futures.ThreadPoolExecutor(...)`, and `__exit__` calls `shutdown(wait=True)`, so after raising `LLMResponseTimeoutError` the block **blocked waiting for the very call the timeout existed to escape**. Measured: 2s timeout, 60s call, returned after 60s. |
| **Resolution** | **Fixed, three changes.** `WORKER_DEADLINE_SECONDS = 180` — a **wall-clock** ceiling covering a whole worker turn including all of its model and tool calls, enforced in `run_worker()` (#19), which is the single choke point all five workers already pass through. Normal turns finish under 40s, so it only catches the pathological ones. `LLM_RESPONSE_TIMEOUT_SECONDS` is now also passed to the client itself in `llm/clients.py`, so it applies on both routes to the model rather than only the invoker's. And `_invoke_once` now uses the shared `run_with_deadline()` (#18) instead of an executor context manager; verified `ok=False kind=LLMErrorKind.TIMEOUT after 2.0s` where it previously took 60. |
| **Prevention** | **A timeout is only meaningful with its unit named.** "150 seconds" said nothing about *150 seconds of what*, and the answer — idle time between reads — is the one quantity that does not bound a slow generation. Any limit the orchestrator places on an agent needs to state whether it bounds silence, wall-clock duration, or consumed budget, because a coding-agent CLI streaming reasoning tokens is precisely a process that is never idle and may still be making no progress. This lands directly on `maestro delegate --timeout`, documented as a *stale-stream* timeout ("force-terminate the CLI after this much silence") — the same blind spot, in the tool this project delegates through, so the dispatcher needs its own wall-clock deadline over the subprocess regardless. Second: **enforce a limit on every path to the resource, or it is not enforced.** The invoker owned the timeout and workers bypassed the invoker; the same asymmetry let #19 through, and the same shape will recur the moment the orchestrator can reach an agent by more than one route. |

## 18. The run prints its summary and the process never exits — `shutdown(wait=False)` does not opt out of the executor's atexit hook

| Field | Detail |
|---|---|
| **Symptom** | `Run finished \| steps=7 \| documents=['outline.txt']` at 13:54:51, and thirteen minutes later the shell had still not returned a prompt. Nothing was logged after the final banner. Indistinguishable, from the terminal, from a pipeline still working. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/`, CPython 3.12.10 on Windows. Two `note_taker` turns had been abandoned by #17's deadline earlier in the same run. |
| **Diagnosis** | **Established by reproducing it in five lines, outside the project.** `concurrent.futures.thread` registers an `atexit` hook that joins every worker thread it has created, and those threads are **not** daemons; `shutdown(wait=False, cancel_futures=True)` cancels *queued* futures and does not opt out of that hook. So every turn abandoned by the deadline left a thread blocked in a socket read, and the interpreter refused to exit until the server finally answered. The reproduction — submit a 30s sleep, `shutdown(wait=False)`, print, exit — printed and then hung, killed at 12s with exit code 124. The interaction is the sharp part: #17's fix *created* this, because before the deadline existed nothing was ever abandoned. |
| **Resolution** | **Fixed.** `run_with_deadline(fn, *, timeout, name)` in `llm/invoker.py` runs the call on a **daemon** thread, which is neither registered with that hook nor joined at shutdown. Both timeout paths — the worker deadline and `_invoke_once` — now share it, which also removed the duplicated thread plumbing. `contextvars.copy_context()` is used so records logged from the thread keep the run's correlation id, and a dedicated `DeadlineExceededError` is raised rather than the builtin `TimeoutError`, documented as "never raised by a provider, so catching it cannot swallow a real transport timeout." Verified end to end: deadline fires on time, normal and error paths unchanged, request id propagates, and the process exits 0 with a worker still mid-`sleep(120)`. |
| **Prevention** | Two, and the second is the one that generalizes. **Nothing in CPython can cancel a thread blocked on a socket read** — the only decision available is whether that thread outlives the process, and `daemon=True` is how you make the answer no. Abandoning work therefore has a cost that must be chosen deliberately: here it is one idle thread and one server slot until the response lands, which is strictly cheaper than paying the deadline twice. And **a cleanup API's name is not its contract**: `wait=False` reads as "do not wait" and the waiting happens somewhere else entirely, at interpreter shutdown, in a hook the calling code never mentions. For the orchestrator, which will abandon agent subprocesses by design, the equivalent question is what a killed adapter leaves behind — an orphaned CLI process holding a worktree lock is this bug with a worse blast radius, and `Architecture.md`'s orphan-reconciliation requirement (ADR-005) is the same argument at process scope. |

## 19. One worker's provider error aborts the whole graph and discards every finished team's work

| Field | Detail |
|---|---|
| **Symptom** | `openai.UnprocessableEntityError: 422` raised out of `doc_writer_agent.invoke()`, through `writing.py:51`, through `orchestrator.py:81`, through `super_graph.stream()`, out of `main.py`, and off the end of the process — a ~90-line traceback ending the run. | **Date** | 2026-08-06 |

| **Resolution** | **Fixed.** `run_worker(agent, name, state)` in `teams/supervisor.py`, which all five worker nodes now route through, and which **always returns a report**: on a deadline miss (#17), `"Worker 'X' ran past its 180s deadline and produced no report. | **Prevention** | The sentence this entry exists for: **a supervisor can route around a worker that failed; it cannot route around a traceback.** Converting an exception into a report is not error-swallowing — it is what makes the failure *routable*, and it preserves the property that matters most, which is that work already on disk survives. Two constraints on doing it correctly, both learned here. The report must say **what state it leaves behind** ("anything it saved before failing is still on disk"), because the next decision depends on that and nothing else can supply it. And the boundary must be at a **choke point**, not per call site: five nodes were each about to grow their own `try`, and the reason there is now one function is the same reason ADR-010 put the wire-format shim on the transport. For the orchestrator this is the agent adapter's contract — an adapter returns a classified outcome and never raises past the router, or a single vendor's bad day costs every worktree in flight. |

| Field | Detail |
|---|---|
| **Symptom** | Two defects, both visible in produced artefacts rather than in any error. (a) `temp/research_results.txt` contained the two characters `\` and `n` everywhere a line break belonged — 3 literal `\n`, 0 real newlines. A guard that only fires against *existing* state has a startup hole — the content guard was written first, was correct, and was useless in the ordering that actually occurred; **check the intent, not just the collision.** And an escaping convention is part of the wire contract: `_unescape` belongs at the tool boundary for the same reason `tgi_compat` belongs on the transport (ADR-010), because asking the model to escape correctly on a decoder that will not let it is not a fix. |

## 29. Windows console-script launchers can mix one Python's site-packages with another's stdlib/DLLs — vendor CLI subprocesses failed importing compiled stdlib modules like `_bz2`

| Field | Detail |
|---|---|
| **Symptom** | Requirements-stage tooling that touches compressed files failed inside an agent subprocess with `ImportError: DLL load failed while importing _bz2`, surfaced while diagnosing `orchestrator_run-20260808-135443` (Document-Loaders run). The failure was environment-shaped rather than logic-shaped: the same tooling worked when run directly from an interactive shell. |
| **Date** | 2026-08-08 (diagnosed from the run's debug log; fixed the same day) |
| **Environment** | Windows 11, orchestrator vendor CLI subprocesses (`claude`, `codex`, `maestro`) launched via `subprocess.run` from `adapters/*.py`, inheriting the parent orchestrator process's environment by default. |

Any subprocess this project spawns that might itself run Python should get an explicitly scrubbed environment rather than an inherited one; `subprocess_env()` is now the one place that decision is made, for every vendor adapter, rather than a fix applied to whichever call site happened to hit it first — the same shape as ADR-010's transport shim. |

| **Prevention** | The unit of rollback must match the unit of judgment. ## 54. Two same-wave coding agents facing the identical problem do not benefit from each other's discovery — `learnings.md` is only consulted before either has hit the problem and after each has already solved it alone

| Field | Detail |
|---|---|
| **Status** | **FIXED — 2026-08-28/2026-08-29, verified in production twice. See Follow-up.** |
| **Symptom** | In `run-20260828-175006`, T-001 and T-002 (parallel `codex`-backend coding tasks, same wave, same base commit) both independently hit the identical `react-transition-group@1.2.1` / React 18 peer-dependency `ERESOLVE` failure and both wrote near-duplicate findings to the run's shared `learnings.md`: `## 2026-08-28 12:53:49Z — T-001` ("npm ci fails dependency resolution because react-transition-group 1.2.1 declares a peer dependency on React ^15 or ^16 ... install requires --legacy-peer-deps") and, ten seconds later, `## 2026-08-28 12:53:59Z — T-002` (same finding, same wording pattern, independently discovered). Neither entry references or builds on the other. The task brief explicitly told both agents to "read the shared learnings file before finishing to check for and apply any discovered issues" — they did read it before finishing, and it made no difference, because by then each had already spent its own turn rediscovering and working around the identical failure. |
| **Date** | 2026-08-28 |
| **Environment** | `orchestrator/wave_orchestrator/dispatch.py` (coding-task briefs), `orchestrator/artifacts.py` (`append-learning`, OS-locked write path), two parallel `codex`-backend worktrees in `run-20260828-175006`. |
| **Root Cause** | **Confirmed from the debug log's own timestamps.** Each agent consults `learnings.md` at exactly two points in its turn: once at the very start (a single `Get-Content` alongside `context.md`, before either agent has attempted anything that could fail), and once at the very end (a final check "before finishing"). T-002's first read happens at `12:52:34Z`, before T-001 has written anything. T-001 independently hits the `ERESOLVE` error itself at `12:53:43Z` and writes its finding at `12:53:49Z`. T-002 independently hits the *same* error via its own `npm` command at `12:53:53Z` — four seconds *after* T-001's entry existed, but T-002 does not re-read `learnings.md` at that point; it only reads it again in its final pre-finish check, by which time it has already worked around the failure on its own and has nothing left to gain from T-001's entry. The write path is not at fault: both entries land intact and in order, and the OS-level lock in `artifacts.py::append_learning()` serializes the two near-simultaneous appends correctly (confirmed by the exact ten-second-apart, non-interleaved timestamps in the file). The gap is architectural — the two read points bracket the moment of discovery on both sides, so a same-wave peer can only ever benefit from a problem some *other, already-finished* task recorded, never from one a live peer is hitting at roughly the same moment. |
| **Resolution** | **Not implemented.** No code change was made; this was found by reading a production run's evidence, not by a targeted investigation. |
| **Recommended Fix** | The task brief already asks agents to "read... before finishing," which only catches a problem some earlier-finishing peer already solved. To let same-wave peers help each other in real time, an agent would need to re-read `learnings.md` **at the moment it hits a failure**, not only at the start and end of its turn — e.g., the coding-agent brief could instruct: "if a command fails unexpectedly, check `learnings.md` again before attempting your own fix, in case another agent already diagnosed it." This costs one extra file read per failure and would have let whichever of T-001/T-002 failed second (T-002, by four seconds) skip its own diagnosis and go straight to `--legacy-peer-deps`. A cheaper, coarser alternative: since both tasks were installing the *same* pinned dependency into *independent* worktrees, install-time failures like this one are arguably not a "learning to discover" problem at all, but a case for a resolved lockfile shared at plan time — which sidesteps the timing gap entirely by never letting two agents redo the same install independently. |
| **Prevention** | Do not assume "the brief tells agents to check shared learnings" delivers real-time knowledge-sharing between concurrent peers. It only delivers knowledge from a *strictly earlier* writer to a *strictly later* reader. For problems likely to be hit simultaneously by multiple same-wave tasks (a shared, newly-pinned dependency; a shared build-tool version; a shared environment quirk), either front-load the discovery into a dedicated dependency-setup task those tasks depend on (this project's own plans have used exactly that pattern elsewhere — a foundational "add the dependency" task with everything else depending on it), or accept that same-wave peers will pay the discovery cost once each, in parallel, and design the acceptance criteria around that rather than around "the second agent will read what the first one found." |
| **Correction (2026-08-29)** | The Symptom field above quotes the task brief as saying "read the shared learnings file before finishing," and this and two other docs (`Architecture.md`'s Artifact and Repository Boundaries section, `Research.md` topic 55) had read that as the reusable coding brief's own design. It is not: `wave_orchestrator/prompts.py`'s `LEARNINGS_SECTION` template has only ever said to read `learnings.md` "at any time," with no scheduled second read point. The "before finishing" wording traced back to `run-20260828-175006`'s own user-supplied goal, which asked agents to check shared learnings "before finishing" as an explicit requirement; that phrasing flowed through requirements → `context.md` → the planner → that run's two task descriptions, and was never part of the durable brief at all. This matters for the fix below: it rules out "give the brief a second scheduled read point," since the brief already granted unlimited reads and they went unused — what was missing was a *trigger*, not permission. |
| **Follow-up (2026-08-29)** | **Fixed.** Implemented as a combination of a prompt change and a mechanical one, chosen from a wider solution survey after this bug was first read back to the user (four option families were laid out: prompt-only triggers, a tool-mediated peer-broadcast wrapper, deterministic wave-level warm-up, and post-turn resume; the user chose the first two). `wave_orchestrator/prompts.py`'s `LEARNINGS_SECTION` now carries two paired instructions: re-read `learnings.md` before diagnosing any command that fails outside the new wrapper below, since a peer may already have the answer; and, for a failure other same-wave agents could plausibly also hit, record the raw symptom the instant it happens rather than the finished diagnosis, since the write side already has a trigger clause ("the moment you find it") that fired correctly in the original run — T-001 wrote six seconds after failing — while the read side had only permission and never fired. A `learnings.stamp` byte-size counter (`read_learnings_stamp()`), bumped atomically inside `append_learning()`'s existing lock, lets `run_shared_command()` skip the peer-read cheaply when nothing has changed. Verified in production twice the same week: `run-20260829-160013` exercised the new prompts but every Copilot-backed task failed immediately on an unrelated regression this same fix introduced (see #56) before the mechanism itself could be exercised; `run-20260829-162143` (all `codex`-backend tasks, same `react-transition-group@1.2.1`/React 18 reproduction as the original bug) showed T-003's own failing `npm test` printing T-002's `ERESOLVE` diagnosis — including the concrete `--legacy-peer-deps` fix — directly beneath its own error output, automatically, without T-003 ever choosing to check `learnings.md`; a second live-peer handoff fired two seconds after discovery in the same run. Full suite: 278 passing, the one pre-existing unrelated Copilot failure. See `Decisions.md` ADR-042 and `Research.md` topics 56–57. |

## 55. `run-shared`'s peer-read cursor defaulted to "now" on a task's first call, silently hiding a peer's finding written moments earlier — the exact race #54 exists to close, relocated into #54's own fix

| Field | Detail |
|---|---|
| **Status** | **FIXED — found and fixed during testing, 2026-08-29, before #54's fix shipped.** |
| **Symptom** | Reproduced directly with a two-task simulation, not from a production log. `run_shared_command()` (see #54) decides what counts as a "new" peer finding by comparing a task's saved cursor (a byte offset into `learnings.md`) against the file's current size. A task's first `run-shared` call, with no cursor file yet on disk, computed a fallback cursor of "`learnings.md`'s current size right now." If a peer had already written a finding by the time this task made its own first `run-shared` call — even though that finding postdated this task's own start-of-turn read — the fallback cursor swallowed it: the peer's entry silently counted as "already known," and no banner ever printed. |
| **Date** | 2026-08-29 |
| **Environment** | `orchestrator/wave_orchestrator/dispatch.py`, `orchestrator/artifacts.py::run_shared_command()`. |
| **Root Cause** | Two independent, coupled defects. (a) Nothing seeded a task's cursor before its turn began, so `run_shared_command()`'s only option on a first call was to fall back to "the stamp right now" — which is correct only if nothing has changed since the task's own actual start-of-turn read, an assumption the whole bug this mechanism exists to fix already disproves. (b) Once seeding was added (writing the cursor to the stamp value *before* dispatch, so it represents what the task's own start-of-turn read actually saw), a second, sharper bug surfaced: `read_learnings_cursor()`'s original fallback used a bare `cursor or read_learnings_stamp(...)` pattern, and Python's `or` treats `0` as falsy — so a task correctly seeded to a legitimate starting cursor of `0` (a run whose `learnings.md` is still empty) was silently overridden by "start from wherever the file is right now," discarding the very seed just written and reintroducing (a)'s exact failure for the one case seeding was supposed to fix first. |
| **Resolution** | **Fixed, both causes.** (a) `wave_orchestrator/dispatch.py:189` now calls `art.write_learnings_cursor(artifacts, task_id, art.read_learnings_stamp(artifacts))` immediately before a task's agent turn starts (before `run_agent()` is called), so the cursor is seeded to match what the task's own start-of-turn read actually saw, not whatever the stamp happens to be by the time the task gets around to its first `run-shared` call. (b) `read_learnings_cursor()` (`artifacts.py:364`) now returns `None` for "never recorded" instead of `0`, and `run_shared_command()` checks `if cursor is None: cursor = read_learnings_stamp(...)` explicitly — a real, freshly-seeded `0` is no longer indistinguishable from "unset." |
| **Prevention** | A cursor/offset value that is legitimately `0` is a recurring trap for any `x or default` fallback pattern in Python — `0`, `""`, and `None` are all falsy, but only `None` here means "nothing was ever recorded." Reserve `None` explicitly for "unset" whenever a valid value can be zero, and check for it with `is None` rather than truthiness. More generally: a mechanism built to fix a same-wave discovery race needs its own bootstrapping moment (the very first read any task makes) audited with the same suspicion as the race itself — this defect was found only because a two-task simulation was run as a sanity check on the mechanism immediately after writing it, not from a design review. |

## 56. `LEARNINGS_SECTION`'s growth to support the `run-shared` mechanism (#54) pushed Copilot's `-p` prompt argv past cmd.exe's ~8,191-character limit, failing every Copilot-backed dispatch

| Field | Detail |
|---|---|
| **Status** | **FIXED — same day, 2026-08-29, found via a live production run.** |
| **Symptom** | `run-20260829-160013`: both Copilot-backed coding tasks (T-001, T-003) failed immediately, in both the initial wave and its rework, with `"The command line is too long."` — 4 failed dispatches total, and the wave orchestrator gave up with `"wave 0 produced nothing usable"` before any of #54's actual fix could be exercised. |
| **Date** | 2026-08-29 |
| **Environment** | `orchestrator/adapters/copilot.py` (`-p <prompt>` argv delivery through `copilot.BAT`, routed through `cmd.exe`), `orchestrator/wave_orchestrator/prompts.py` (`LEARNINGS_SECTION`). |
| **Root Cause** | Copilot's adapter passes the entire assembled prompt as a literal `-p <prompt>` command-line argument, and on Windows that argument is subject to `cmd.exe`'s ~8,191-character total command-line limit (measured exactly via `subprocess.list2cmdline()` against the real argv, including `--available-tools`, `--add-dir`, and the worktree path). Before this session's `LEARNINGS_SECTION` edit (#54), a representative coding task's full assembled prompt left about 1,295 characters of headroom under that limit. The edit that instructed agents to use the new `run-shared` command and gave two full command examples added 1,729 characters to the template — pushing the same representative prompt roughly 684 characters over the limit. Codex was unaffected only because it delivers its prompt over stdin, not argv, so this only ever surfaced through Copilot-backed dispatches. |
| **Resolution** | **Fixed.** `LEARNINGS_SECTION`'s prose was trimmed — both command examples were kept (the `run-shared` example is the mechanism's own "hard floor," see #54) but the surrounding sentences and a redundant third repetition of the artifact path were cut. Verified with the same `subprocess.list2cmdline()` measurement against the same representative task: margin recovered to about 887 characters — less than the pre-#54 baseline of 1,295, a real, permanent narrowing of headroom, but positive again. A regression-guard test, `test_the_coding_prompt_stays_within_copilots_argv_budget` (`orchestrator/tests/test_wave_orchestrator.py:177`), now asserts the assembled prompt's Windows command-line length against Copilot's real argv shape, so a future prompt edit that reintroduces this cannot land silently. |
| **Prevention** | Any prompt-template edit shared across all coding-agent backends must be checked against the narrowest backend's delivery mechanism, not just against "does the text read well" — Codex's stdin delivery has no such ceiling, which is exactly what let this land unnoticed until a live Copilot dispatch hit it. The regression-guard test now enforces this mechanically going forward, but the underlying fragility is not fully closed: even the restored ~887-character margin is a soft budget an unusually verbose planner-generated task description could still exceed. A more durable fix — changing how `adapters/copilot.py` delivers the prompt (stdin or a temp file, as Codex and Claude already do) rather than relying on staying under a fixed argv ceiling — was identified but is out of scope for this fix and remains open. |

## 57. `run-shared`'s child process inherits Windows' cp1252 console codepage standalone, and crashes writing the em dash in `learnings.md`'s own entry headers

| Field | Detail |
|---|---|
| **Status** | **FIXED — same day, 2026-08-29, found via manual testing before shipping.** |
| **Symptom** | `python artifacts.py run-shared <shared_dir> <task_id> -- <command>`, run as its own OS process (over Bash, not imported — the same invocation coding agents use), raised `UnicodeEncodeError` / `UnicodeDecodeError` the moment a peer-findings banner containing a `learnings.md` entry header reached stdout/stderr. Every entry header `append_learning()` writes contains an em dash (`## <timestamp> — <agent>`), the same character `Bugs.md` #11 already named as the thing bare `cp1252` output dies on. |
| **Date** | 2026-08-29 |
| **Environment** | `orchestrator/artifacts.py::_cli()`, invoked as a standalone process via `run-shared`. |
| **Root Cause** | Every other write path in `artifacts.py` opens files with `encoding="utf-8"` explicitly, but `run-shared`'s own stdout/stderr streams are supplied by the OS process launch itself, not opened by this module — so they default to whatever console codepage Windows handed the fresh process (`cp1252`, typically), not the UTF-8 the rest of the module assumes throughout. Printing a peer's `learnings.md` entry verbatim (including its em-dash header) to that stream crashed. This is the same defect class as `Bugs.md` #11, on stdout/stderr instead of file I/O. |
| **Resolution** | **Fixed.** `_cli()` now reconfigures `sys.stdout` and `sys.stderr` to UTF-8 (`stream.reconfigure(encoding="utf-8", errors="replace")`, guarded for the `AttributeError`/`ValueError` a stream that does not support reconfiguration would raise) as the very first thing it does, before any argument parsing or peer-finding output. |
| **Prevention** | Any CLI entry point launched as its own OS process — as opposed to code imported and run inside an already-configured parent process — needs its own explicit encoding setup; inheriting the parent's `PYTHONUTF8`/`PYTHONIOENCODING` environment is not guaranteed, and Windows' default console codepage is the one place this codebase has now hit the same em-dash crash twice in two different I/O paths (file writes in #11, stdout/stderr here). Worth a repo-wide sweep the next time a new standalone entry point is added, rather than fixing each occurrence only after it crashes in testing. |
