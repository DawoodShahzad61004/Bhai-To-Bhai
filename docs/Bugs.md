## 5. Tutorial supervisor node will crash on first invocation — `LLMResult` subscripted as a dict, no structured-output binding

| Field                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Symptom**     | **Not yet observed.** `research_builder.py` compiles the graph and renders the PNG but never invokes it, so the supervisor body has never executed. On the first `.invoke()` or `.stream()` it will raise `TypeError: 'LLMResult' object is not subscriptable` at `yt-tutorial/state.py:27`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Date**        | 2026-08-04 (identified by reading)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Environment** | `yt-tutorial/`, Python 3.12.10, `langgraph` 1.2.10, `langchain` 1.3.14.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Diagnosis**   | **Established statically, two coupled defects.** (a) `state.py:26-27` does `response = llm_invoke(llm, messages)` then `goto = response["next"]`, but `llm_invoke` is declared `-> LLMResult` (`llm_caller.py:838`) and `LLMResult` is a plain `@dataclass` with no `__getitem__`; the model's text is at `response.content`, and success is signalled by `response.ok`, which is not checked either. (b) More fundamentally, the structured-output layer the tutorial's design depends on is **absent entirely** — there is no `Router` TypedDict declaring `next: Literal[*options]` and no `.with_structured_output(Router)` binding on the LLM. Even with (a) corrected to read `.content`, the supervisor would be parsing free-form model prose for a routing decision, and any value not matching a member name or `FINISH` would fail against the `Command[Literal[*members, END]]` annotation. Two cosmetic issues sit alongside: `make_supervisor_node` is annotated `-> str` when it returns a callable, and the system prompt is assembled from adjacent f-strings that concatenate without a space (`"between the" "following workers"`). |
| **Resolution**  | **Fixed (2026-08-05).** Both defects addressed in what is now `yt-tutorial/teams/supervisor.py`: a `Router` TypedDict with `next: Literal[*options]` is bound via `.with_structured_output(Router, method=...)`, and the bound runnable is passed *through* `llm_invoke` rather than around it, so the supervisor keeps the FIFO gate and 429 handling — the more useful of the two directions this field originally proposed. `result.ok` is now checked before the subscript, so a transport failure raises a readable `RuntimeError` instead of a `TypeError` five frames deep.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Prevention**  | The specific trap is that a graph **compiling is not evidence that it runs** — LangGraph validates node registration and edge targets at `.compile()`, and nothing inside a node body is checked until it executes. The general lesson matters more for this project than the tutorial: when porting a module across projects (ADR-009), its return *type* is part of its contract and does not survive being assumed. Worth a smoke invocation as the definition of done for any graph, not a successful compile.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## 5a. Follow-up on #5 (2026-08-05) — fired as predicted, plus a third defect reading had missed

| Field | Detail |
|---|---|
| **Outcome** | #5 fired on the first invocation with exactly the predicted traceback: `TypeError: 'LLMResult' object is not subscriptable` at `state.py:27`. The static diagnosis needed no revision. |
| **Third defect** | Found only while fixing the first two. `State` was `class State(MessagesState): pass` — no `next` key — while the supervisor returned `update={"next": goto}`. LangGraph **silently discards** updates addressed to channels absent from the state schema; verified directly with a minimal two-node graph, which ran to completion and returned state with no `next` field rather than raising. That write had always been a no-op. `next: str` is now declared in `teams/state.py`. |
| **Prevention** | An unknown *edge target* is a compile-time error; an unknown *state key* is not an error at all. State-schema drift is therefore the quieter of the two failure modes, and the one that matters more here, since the Canonical Task Context Store is precisely a schema that many writers update. Any canonical-context write path should reject unknown keys explicitly rather than inherit a framework's silent-drop behaviour. |

## 6. Ported `llm_caller.py` adaptive cooldown silently degrades to zero against the configured OpenAI-compatible endpoint

| Field                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Symptom**     | **Not yet observed, and by design will produce no error when it happens.** The adaptive inter-call cooldown in `yt-tutorial/llm_caller.py` will compute a floor of `0.0` on every call, disabling the throttle that exists to stop back-to-back calls draining the token window. The only signal is a `logger.debug` line: `could not extract rate-limit headers — cooldown base will be 0`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Date**        | 2026-08-04 (identified by reading)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Environment** | `yt-tutorial/llm_caller.py` ported from `RAG-work` (ADR-009); `llm_setup.py` configures four `ChatOpenAI` clients against a custom OpenAI-compatible base URL (`CUSTOM_API_BASE`), with the original `ChatGroq` clients commented out.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Diagnosis**   | **Established statically.** The cooldown floor is derived from Groq's `x-ratelimit-remaining-tokens` / `-limit-tokens` / `-reset-tokens` response headers, which `_parse_token_headers` (`llm_caller.py:699`) reads from `_captured_response_headers`. That global is populated only by `_on_groq_response`, attached by `_install_header_hook` (`:97`), which walks `llm.client._client` and returns early unless the result `isinstance(..., httpx.Client)`. For `ChatOpenAI`, `llm.client` is the OpenAI SDK's `Completions` resource and `._client` is the `OpenAI` client object, not an `httpx.Client` — so the hook silently declines to attach and the global stays `None`. Both documented fallbacks then miss as well: LangChain's `ChatOpenAI` puts `token_usage` / `model_name` / `finish_reason` in `response_metadata`, not `headers`. `_parse_token_headers` returns `(0.0, 0.0, 0.0)`, and `_compute_cooldown_base` yields `0.0`. Even if the hook did attach, a non-Groq server is unlikely to emit Groq's header names or its duration format (`_parse_groq_duration`). **Scope of the defect is narrow and should not be overstated**: the FIFO gate, retry/backoff, the global token-reset deadline, the `LLMRateLimitAbortError` threshold, and the error taxonomy all still function — the taxonomy explicitly catches both `groq.*` and `openai.*` exception classes. Only the *header-derived cooldown floor* is inert. |
| **Resolution**  | **Open, and accepted for now** — this is sandbox code (ADR-008) and the degradation is graceful. The fix is to make header extraction vendor-pluggable: attach the hook by inspecting the actual transport rather than assuming a Groq client shape, and read header names from configuration.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Prevention**  | The dangerous property here is not the bug but its **silence** — a crash would have surfaced on the first run, whereas a throttle that quietly becomes a no-op only shows up as unexplained rate limiting much later. This is a direct rehearsal of a risk ADR-006 already names: vendor-specific strings and header names belong in configuration, not in code, and a *derived* safety value that silently defaults to "no protection" should log at warning level or refuse to start, not at debug. When the budget ledger is built, an inability to read consumption must be a visible degraded state in the ledger, never an implicit zero.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 7. TGI 3.0 diverges from the OpenAI tool-call wire format in both directions, and an agent loop hits both on consecutive turns

| Field | Detail |
|---|---|
| **Symptom** | Two failures that looked unrelated and turned out to be one round trip. First, on any tool-calling turn: `pydantic_core.ValidationError: 1 validation error for AIMessage / invalid_tool_calls.0.args / Input should be a valid string [type=string_type, input_value={'next': 'doc_writer'}, input_type=dict]`, raised inside `langchain_openai`'s `_convert_dict_to_message`. After that was fixed, a second failure appeared one turn later, on the model call that follows a tool result: `openai.InternalServerError: Internal Server Error` from `doc_writer`. Between them sat the misleading evidence that the tool itself had succeeded — `Writing document...` printed, and the file was on disk. |
| **Date** | 2026-08-05 |
| **Environment** | `yt-tutorial/`, local TGI at `CUSTOM_API_BASE`, `system_fingerprint: 3.0.0-sha-8f326c9`, model `llama-3.1-8b-instruct`. Client `langchain-openai` 1.4.1 / `langchain-core` 1.5.3 / `openai` SDK, Python 3.12.10. |
| **Diagnosis** | **Established by bisection against the live server, three response deviations and one request deviation.** On responses TGI returns tool-call `arguments` as a JSON **object** where the OpenAI API returns a JSON **string**, and `langchain-core` validates it as `str`; it **omits `content` entirely** on tool-call turns, where langchain requires the key; and it labels every tool call `id: "0"`, so a multi-turn transcript accumulates several calls and results sharing one identifier with nothing pairing up. Normalizing the first two yields an `AIMessage(content="")` — and on the *next* turn langchain serializes that back out as `"content": null` (confirmed directly: `_convert_message_to_dict(AIMessage(content="", tool_calls=[...]))` → `{"content": null, ...}`), which TGI rejects. Five request shapes were sent to the live server differing only in that field, and exactly one failed: `user` alone → 200; `user + assistant(tool_calls)` → 200; `+ tool result` → 200; **same with `content: null` → 500**; tool result with no `tools` in the request → 200. So the asymmetry is closed-loop: TGI will not emit `content`, langchain converts its absence to `null` on the way back, and TGI will not accept `null`. A single-call consumer never sees it, which is why the supervisor worked while every worker died on its second turn. |
| **Resolution** | **Fixed.** `yt-tutorial/llm/tgi_compat.py` (142 lines) — an `httpx.HTTPTransport` subclass normalizing traffic in both directions: inbound, `arguments` dict → JSON string, missing `content` → `""`, `id: "0"` → a generated unique id, and TGI's non-spec `"description": null` dropped; outbound, assistant `content: null` → `""`. Streaming (`text/event-stream`) and non-`/chat/completions` paths pass through untouched. Verified by A/B on an identical payload against the live server: default transport 500, compat transport 200; and against a stub reproducing TGI's exact captured bytes, where the same supervisor call raises `ValidationError` without the shim and returns `Command(update={'next': 'note_taker'}, goto='note_taker')` with it. |
| **Prevention** | Two lessons, and the second is the one that generalizes. **"OpenAI-compatible" is a claim about the request schema, not a contract about the response** — three of these four deviations are in what the server *sends back*, which no amount of reading the client's documentation would have predicted. Probe an endpoint's actual bytes before building on it. And **normalize at the boundary, once**: the shim went on the HTTP transport rather than into the supervisor because every agent in the system traverses the same path, and the first fix attempt — patching the supervisor — would have left all five workers broken. This is the direct rehearsal of the orchestrator's adapter layer: each vendor CLI will have its own equivalent of `arguments`-as-dict, and the place to absorb it is the adapter, never the router or the workflow code that consumes it. |

| **Date** | 2026-08-05 |
| **Environment** | As #7. `langchain-openai` 1.4.1, whose `with_structured_output()` defaults to `method="json_schema"`. |
| **Diagnosis** | **Established by capability probe.** Four request shapes were sent directly to `/v1/chat/completions`, identical but for how structure was requested: plain chat → **200**; `response_format: {"type": "json_object"}` → **500**; `response_format: {"type": "json_schema", ...}` → **500**; `tools: [...]` (function calling) → **200**. TGI 3.0 implements neither `response_format` mode, and `json_schema` is exactly what langchain-openai 1.4.1 sends by default. A follow-up probe confirmed function calling is not merely accepted but usable: with `tool_choice: "auto"` and with a forced `{"type": "function", "function": {"name": "Router"}}`, the server returned a well-formed call each time and respected the parameter `enum`, selecting only declared member names. Note this defect was **predicted before it fired** — a stub server built while the real endpoint was down logged the outgoing mode as `json_schema`, which is what prompted probing for it. |
| **Resolution** | **Fixed.** `STRUCTURED_OUTPUT_METHOD = "function_calling"` in `yt-tutorial/config.py`, passed as `llm.with_structured_output(Router, method=STRUCTURED_OUTPUT_METHOD)` in `teams/supervisor.py`. The `Router` TypedDict becomes an ordinary tool schema, so routing rides the same mechanism as every other tool call — which also means it inherits #7's shim rather than needing a second workaround. The constant lives in config precisely because it is a property of the deployed server, not of this code. |
| **Prevention** | A client library's *default* encodes an assumption about the server, and defaults are the least visible form of coupling — nothing in the calling code named `json_schema`. Where a capability has several negotiable encodings, the choice belongs in configuration keyed to the deployment, with the working set established by probe rather than by documentation. Directly relevant to ADR-006's unresolved DeepSeek question and to any orchestrator adapter pointed at a custom OpenAI-compatible endpoint: "it speaks the OpenAI API" needs decomposing into a per-feature capability matrix before an adapter can rely on any of it. |

## 9. Worker agents cannot terminate on their own, and bounding them relocated the loop to the supervisor

| Field | Detail |
|---|---|
| **Symptom** | `python main.py` printed one supervisor decision followed by 80+ consecutive `Writing document...` lines, then eventually a 500 as the transcript outgrew the server's input limit. With `recursion_limit` lowered to reproduce it quickly: `GraphRecursionError: Recursion limit of 8 reached without hitting a stop condition`, raised inside `doc_writer_agent.invoke()` — the inner ReAct loop, not the outer graph. |
| **Date** | 2026-08-05 |
| **Environment** | As #7. `langchain.agents.create_agent` over `write_document` / `edit_document` / `read_document`. |
| **Diagnosis** | **Established by controlled A/B against the live server, and the result is a property of the serving stack rather than a defect in this code.** The same four-message conversation was sent twice, differing only in whether `tools` was present in the request. With `tools` → another `write_document` call and empty `content`. Without `tools` → a complete, well-formed final essay as ordinary text. TGI grammar-constrains generation to the attached tool schemas, so while tools are bound the model **structurally cannot emit a final answer**; the ReAct loop's exit condition — an assistant turn with content and no tool calls — is unreachable. Prompt-level remedies were tried and failed: adding an explicit `finish_work` tool alongside a "call this when the work is complete" instruction produced *another* `write_document` call. A message trace showed the model rewriting the same file with slightly different prose on each pass, never converging. **Bounding the worker then moved the loop up one level rather than closing it.** `ToolCallLimitMiddleware(..., exit_behavior="end")` terminates the run with a bookkeeping stub as the final message — `Tool call limit reached: run limit exceeded (4/3 calls)` — and that stub was being handed to the supervisor as the worker's report, where it reads as unfinished work; the supervisor re-routed to the same worker indefinitely. |
| **Resolution** | **Fixed, at two layers, both in code rather than in prompts.** `tool_call_limit()` in `teams/supervisor.py` wraps every worker in `ToolCallLimitMiddleware(run_limit=TOOL_CALL_RUN_LIMIT, exit_behavior="end")`; `agent_report()` replaces the terminal stub with a description of what the worker actually did, derived from the tool calls in its message history (`Finished. Tools executed: write_document(essay.txt), ...`). Both constants are in `config.py` with the reasoning attached. Verified: the writing graph now reaches `FINISH` and returns `{'supervisor': None}` instead of exhausting the recursion limit. |
| **Prevention** | Three notes. First, and most useful to this project: **when a model cannot be relied on to decide it is finished, the bound must be structural** — this is the same argument the deterministic check runner rests on, arriving from the model side rather than the verification side, and it was reached here only after two prompt-level attempts demonstrably failed. Second, a guard that ends a run leaves *its own* artefact in the transcript, and if a downstream consumer reads that artefact as content, the loop simply moves; whatever ends a run must also say what the run accomplished. Third, a known residual: `agent_report()` counts *requested* tool calls, including the one the limit blocked, so it over-reports by one — visible in `run_logs/agent_run_20260805_162018.debug.log`, where the report names four `write_document` calls while only three executed. Harmless as a supervisor hint, wrong as an audit record, and the orchestrator's event log cannot afford the same conflation of "attempted" with "executed". |

## 10. `os.path.join` with an absolute tail escaped the workspace sandbox and drove a self-reinforcing rewrite loop

| Field | Detail |
|---|---|
| **Symptom** | Inside the `doc_writer` loop of #9, a message trace showed the model's `file_name` argument mutating across turns: `essay.txt`, then `essay.txt` again, then the full `C:\Users\LOQ\Desktop\Projects\Bhai-To-Bhai\yt-tutorial\temp\essay.txt`. Every call still reported success. |
| **Date** | 2026-08-05 |
| **Environment** | `yt-tutorial/tools.py` (now `tools/documents.py`), Windows 11, Python 3.12.10. |
| **Diagnosis** | **Established, and it is two problems sharing one line.** The tools built their path as `os.path.join(os.getcwd(), "temp", file_name)` and returned `f"Document saved to: {file_to_use}"` — the **absolute** path. `os.path.join` discards everything before an absolute component, verified directly: joining the workspace prefix with an absolute tail returns the tail unchanged. So the tool announced a path, the model echoed that path back as `file_name`, and `join` honoured it — a perfect fixed point, and the engine driving the rewrite loop. The same line is a **sandbox escape**: any `file_name` the model chose to make absolute placed the write anywhere the process could reach, and nothing in the tool constrained it. Fixing this reduced but did not end the looping, which is what isolated #9's grammar constraint as the actual cause rather than this. |
| **Resolution** | **Fixed.** `_workspace_path()` in `tools/documents.py` resolves every name as `os.path.join(WORKSPACE_DIR, os.path.basename(file_name))`, with a debug line whenever `basename` changes the argument, and all four tools now return the bare basename rather than the absolute path — closing the feedback loop at its source as well as the escape. |
| **Prevention** | The general form is that **a tool's return value is model input**, so anything it echoes will come back as an argument; returning an absolute path invited exactly the argument that broke the resolver. The security form matters more for the orchestrator: path containment must be enforced by construction at the boundary, never by trusting a well-formed argument, since the argument's author is a language model. Related and unfixed by choice: `tools/code.py` runs model-generated code through `PythonREPL`, i.e. `exec()` in-process with full user privileges and no sandbox — acceptable in a local sandbox, recorded in the module docstring, and not acceptable in anything the orchestrator ships. |

## 11. Three defects in the tool layer that only execution could surface: an undefined name, ANSI-codepage writes, and exceptions that killed the graph

| Field | Detail |
|---|---|
| **Symptom** | Three unrelated failures with one thing in common — all in `tools.py`, none reachable by compiling. (a) `python_repl_tool` returned `Error occurred while executing Python code: name 'repl' is not defined` for every input. (b) `UnicodeEncodeError: 'charmap' codec can't encode character '\u2011' in position 823` while writing a document — after a *successful* model tool call. (c) `FileNotFoundError: [Errno 2] No such file or directory: '...\temp\outline.txt'` propagating out of `read_document` through `ToolNode` and terminating the entire graph run. |
| **Date** | 2026-08-05 |
| **Environment** | `yt-tutorial/tools.py` (now `tools/documents.py`, `tools/code.py`), Windows 11, Python 3.12.10. |
| **Diagnosis** | **Established, three independent causes.** (a) `repl` was never defined anywhere in the project — grep confirmed the name existed at exactly one site, its use. Every call raised `NameError`, and the tool's own `except Exception` converted that into a returned string, so the tool had never worked and had never once *looked* broken to the agent. (b) Bare `open()` on Windows defaults to the ANSI codepage (cp1252), and em dashes, smart quotes, and non-breaking hyphens are routine in model output; the tool call was correct and the write killed it. (c) `read_document` and `edit_document` raised on a missing file, while `python_repl_tool` in the same module returned its error as text — so a single hallucinated filename ended a run that the agent could otherwise have recovered from, and the two conventions sat side by side in one file. |
| **Resolution** | **Fixed, all three.** (a) `from langchain_experimental.utilities import PythonREPL` with a module-level instance, verified end to end. (b) `encoding="utf-8"` on all four file operations; confirmed by having a model write an em-dash-heavy document that previously crashed. (c) `read_document` and `edit_document` now return `Error: no document named X. Available documents: <listing>`, and the out-of-bounds line check in `edit_document` was given the same treatment — the listing lets the agent self-correct rather than merely reporting failure. |
| **Prevention** | (a) is the sharpest of the three: **a broad `except` around undefined-name errors turns a startup crash into a permanent silent malfunction**, and the returned string was shaped like a normal result, so nothing upstream could distinguish it. Catch what the operation can raise, not everything. (b) is a portability default worth pinning project-wide — `encoding="utf-8"` explicitly, everywhere, since the failure depends on the machine's locale rather than the code. (c) generalizes to the orchestrator's agent adapters: a recoverable failure reported *to* the agent and an unrecoverable failure raised *past* it are different mechanisms, the choice between them must be deliberate, and it must be consistent across every tool an agent can reach. |

## 12. A sub-graph invoked without its own config inherits the parent's recursion budget

| Field | Detail |
|---|---|
| **Symptom** | `langgraph.errors.GraphRecursionError: Recursion limit of 2 reached without hitting a stop condition`, raised at `super_builder.py:18` — inside `research_graph.invoke(...)`, not in the top-level graph whose config set the limit. Raising the top-level limit to 25 moved the same error to a limit of 25, still raised inside the sub-graph. |
| **Date** | 2026-08-05 |
| **Environment** | `yt-tutorial/`, `langgraph` 1.2.10, three nesting levels: orchestrator graph → team graph → ReAct agent graph. |
| **Diagnosis** | **Established, and the misleading part is the name.** `recursion_limit` bounds *super-steps in one invocation*, not nesting depth — nothing recurses. `main.py` passed `{"recursion_limit": 2}`, which the orchestrator spent immediately (`START → supervisor` is step 1, `→ research_team` is step 2). More consequentially, `research_graph.invoke()` was called **with no config of its own**, and LangGraph propagates the parent config into sub-graphs, so the research team inherited a budget of 2 for a supervisor↔worker cycle that needs several. With three nesting levels drawing on one shared allowance, the level that exhausts it is not the level that misconfigured it — which is why the traceback pointed at the sub-graph. |
| **Resolution** | **Fixed.** `SUPER_GRAPH_RECURSION_LIMIT = 50` and `TEAM_RECURSION_LIMIT = 25` in `config.py`; `teams/orchestrator.py` passes an explicit `TEAM_CONFIG` on every sub-graph invocation, so a team that spins cannot draw down the orchestrator's budget or starve the other team. The message wrapping at the same call site was corrected too — `{"messages": state["messages"][-1]}` passed a single message where a list is contracted; `add_messages` was coercing it, which made it work by accident. |
| **Prevention** | Two notes. **An inherited budget is a shared budget**, and a shared resource silently consumed by a nested consumer is the miniature form of exactly what ADR-006's ledger exists to prevent — the orchestrator's per-agent allowances need explicit per-level allocation for the same reason, or a runaway sub-task spends the parent task's headroom and the failure surfaces somewhere other than its cause. And separately: `recursion_limit` is a **backstop, not a termination strategy**. Reaching it is always a crash that loses the run, never a clean finish, so a system that relies on it to stop has no termination design — which is what #9's caps and #13's are actually for. |

## 15. The full pipeline runs to a clean FINISH having produced nothing — the guard that stops the loop also ends the task

| Field | Detail |
|---|---|
| **Symptom** | **No error, no traceback, exit code 0.** `run_logs/agent_run_20260805_163729.debug.log` records the complete end-to-end run: 5 steps, a clean `Run finished | steps=5 | documents=none`. The request had asked for the results to be compiled into `research_results.txt`. No file was written, and `writing_team` was never entered — `>>> writing_team starting` does not appear in the log. |
| **Date** | 2026-08-05 (found by reading the run log, not by observing a failure) |
| **Environment** | `yt-tutorial/`, full three-level hierarchy, `llama-3.1-8b-instruct` on TGI. All of #7–#14 already fixed. |
| **Diagnosis** | **Established from the log, and it is the direct cost of #13's fix.** The top-level supervisor routed to `research_team` at step 1; the team reported at step 2; at step 3 the supervisor **routed to `research_team` again** rather than to `writing_team`, despite `TOP_LEVEL_SCOPE` explicitly instructing it to route research before writing; the team reported a near-identical string at step 4; at step 5 the supervisor selected `research_team` a third time and `MAX_WORKER_REPORTS` forced `Command(goto=END)`. The run then terminated normally. So the same guard that converts #13's infinite loop into a bounded run also converts it into a **silent no-op** when the model never routes to the worker that would have done the work. The research team's own final report even asserts that *"The tools can be compiled in a file named 'research_results.txt'"* — a claim of completion for an action nothing performed. Three `forcing FINISH` warnings appear in that one run, two inside the research team and one at the top level. |
| **Resolution** | **Open, and deliberately not patched.** Raising `MAX_WORKER_REPORTS` would restore the loop; making the cap per-worker rather than terminal (block the repeat, let the supervisor pick another target) is the obvious next step and is untested. The honest reading is that the mechanical pipeline is sound and the *routing quality* is bounded by an 8B model driving a three-team delegation, so this is not fully fixable at the code layer — which is the finding, not an excuse for it. |
| **Prevention** | This is the most important entry of the set for the orchestrator, on two counts. **A run that ends cleanly is not a run that succeeded.** Every completion signal available here — exit code, `FINISH`, step count, absence of exceptions, and the agent's own summary — reported success on a run that produced nothing; only comparing the artefacts against the request revealed it. That is precisely why `Architecture.md` maps `FINISH → deterministic check pass` and why ADR-004 subordinates Maestro's own completion signals: a self-reported completion is not evidence, and here is a concrete case where five independent self-reports agreed and were all wrong. **And a safety guard is a behaviour change, not just a safety property** — the cap was introduced to bound a loop and silently acquired the power to abandon a task, with the same log line (`forcing FINISH`) covering both. Any bound the orchestrator places on an agent's work — attempt caps, budget headroom, fix-loop limits — needs to distinguish *"stopped because done"* from *"stopped because bounded"* in what it records, or the audit trail will report the second as the first. Worth noting separately that this defect was found only because the persistent run log existed; nothing on the console distinguished this run from a successful one. |
