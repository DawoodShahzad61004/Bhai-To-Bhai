## 6. Ported `llm_caller.py` adaptive cooldown silently degrades to zero against the configured OpenAI-compatible endpoint

| Field                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Symptom**     | **Not yet observed, and by design will produce no error when it happens.** The adaptive inter-call cooldown in `yt-tutorial/llm_caller.py` will compute a floor of `0.0` on every call, disabling the throttle that exists to stop back-to-back calls draining the token window. The only signal is a `logger.debug` line: `could not extract rate-limit headers — cooldown base will be 0`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Date**        | 2026-08-04 (identified by reading)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Environment** | `yt-tutorial/llm_caller.py` ported from `RAG-work` (ADR-009); `llm_setup.py` configures four `ChatOpenAI` clients against a custom OpenAI-compatible base URL (`CUSTOM_API_BASE`), with the original `ChatGroq` clients commented out.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Diagnosis**   | **Established statically.** The cooldown floor is derived from Groq's `x-ratelimit-remaining-tokens` / `-limit-tokens` / `-reset-tokens` response headers, which `_parse_token_headers` (`llm_caller.py:699`) reads from `_captured_response_headers`. That global is populated only by `_on_groq_response`, attached by `_install_header_hook` (`:97`), which walks `llm.client._client` and returns early unless the result `isinstance(..., httpx.Client)`. For `ChatOpenAI`, `llm.client` is the OpenAI SDK's `Completions` resource and `._client` is the `OpenAI` client object, not an `httpx.Client` — so the hook silently declines to attach and the global stays `None`. Both documented fallbacks then miss as well: LangChain's `ChatOpenAI` puts `token_usage` / `model_name` / `finish_reason` in `response_metadata`, not `headers`. `_parse_token_headers` returns `(0.0, 0.0, 0.0)`, and `_compute_cooldown_base` yields `0.0`. Even if the hook did attach, a non-Groq server is unlikely to emit Groq's header names or its duration format (`_parse_groq_duration`). **Scope of the defect is narrow and should not be overstated**: the FIFO gate, retry/backoff, the global token-reset deadline, the `LLMRateLimitAbortError` threshold, and the error taxonomy all still function — the taxonomy explicitly catches both `groq.*` and `openai.*` exception classes. Only the *header-derived cooldown floor* is inert. |
| **Resolution**  | **Open, and accepted for now** — this is sandbox code (ADR-008) and the degradation is graceful. The fix is to make header extraction vendor-pluggable: attach the hook by inspecting the actual transport rather than assuming a Groq client shape, and read header names from configuration.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Prevention**  | The dangerous property here is not the bug but its **silence** — a crash would have surfaced on the first run, whereas a throttle that quietly becomes a no-op only shows up as unexplained rate limiting much later. This is a direct rehearsal of a risk ADR-006 already names: vendor-specific strings and header names belong in configuration, not in code, and a *derived* safety value that silently defaults to "no protection" should log at warning level or refuse to start, not at debug. When the budget ledger is built, an inability to read consumption must be a visible degraded state in the ledger, never an implicit zero.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 7. TGI 3.0 diverges from the OpenAI tool-call wire format in both directions, and an agent loop hits both on consecutive turns

| Field | Detail |
|---|---|
| **Symptom** | Two failures that looked unrelated and turned out to be one round trip. First, on any tool-calling turn: `pydantic_core.ValidationError: 1 validation error for AIMessage / invalid_tool_calls.0.args / Input should be a valid string [type=string_type, input_value={'next': 'doc_writer'}, input_type=dict]`, raised inside `langchain_openai`'s `_convert_dict_to_message`. After that was fixed, a second failure appeared one turn later, on the model call that follows a tool result: `openai.InternalServerError: Internal Server Error` from `doc_writer`. Between them sat the misleading evidence that the tool itself had succeeded — `Writing document...` printed, and the file was on disk. |
| **Date** | 2026-08-05 |
| **Environment** | `yt-tutorial/`, local TGI at `CUSTOM_API_BASE`, `system_fingerprint: 3.0.0-sha-8f326c9`, model `llama-3.1-8b-instruct`. Client `langchain-openai` 1.4.1 / `langchain-core` 1.5.3 / `openai` SDK, Python 3.12.10. |
| **Diagnosis** | **Established by bisection against the live server, three response deviations and one request deviation.** On responses TGI returns tool-call `arguments` as a JSON **object** where the OpenAI API returns a JSON **string**, and `langchain-core` validates it as `str`; it **omits `content` entirely** on tool-call turns, where langchain requires the key; and it labels every tool call `id: "0"`, so a multi-turn transcript accumulates several calls and results sharing one identifier with nothing pairing up. Normalizing the first two yields an `AIMessage(content="")` — and on the *next* turn langchain serializes that back out as `"content": null` (confirmed directly: `_convert_message_to_dict(AIMessage(content="", tool_calls=[...]))` → `{"content": null, ...}`), which TGI rejects. Five request shapes were sent to the live server differing only in that field, and exactly one failed: `user` alone → 200; `user + assistant(tool_calls)` → 200; `+ tool result` → 200; **same with `content: null` → 500**; tool result with no `tools` in the request → 200. So the asymmetry is closed-loop: TGI will not emit `content`, langchain converts its absence to `null` on the way back, and TGI will not accept `null`. A single-call consumer never sees it, which is why the supervisor worked while every worker died on its second turn. |
| **Resolution** | **Fixed.** `yt-tutorial/llm/tgi_compat.py` (142 lines) — an `httpx.HTTPTransport` subclass normalizing traffic in both directions: inbound, `arguments` dict → JSON string, missing `content` → `""`, `id: "0"` → a generated unique id, and TGI's non-spec `"description": null` dropped; outbound, assistant `content: null` → `""`. Streaming (`text/event-stream`) and non-`/chat/completions` paths pass through untouched. Verified by A/B on an identical payload against the live server: default transport 500, compat transport 200; and against a stub reproducing TGI's exact captured bytes, where the same supervisor call raises `ValidationError` without the shim and returns `Command(update={'next': 'note_taker'}, goto='note_taker')` with it. |
| **Prevention** | Two lessons, and the second is the one that generalizes. **"OpenAI-compatible" is a claim about the request schema, not a contract about the response** — three of these four deviations are in what the server *sends back*, which no amount of reading the client's documentation would have predicted. Probe an endpoint's actual bytes before building on it. And **normalize at the boundary, once**: the shim went on the HTTP transport rather than into the supervisor because every agent in the system traverses the same path, and the first fix attempt — patching the supervisor — would have left all five workers broken. | Field | Detail |
|---|---|
| **Symptom** | Inside the `doc_writer` loop of #9, a message trace showed the model's `file_name` argument mutating across turns: `essay.txt`, then `essay.txt` again, then the full `C:\Users\LOQ\Desktop\Projects\Bhai-To-Bhai\yt-tutorial\temp\essay.txt`. Every call still reported success. |

Measured: 2s timeout, 60s call, returned after 60s. |
| **Resolution** | **Fixed, three changes.** `WORKER_DEADLINE_SECONDS = 180` — a **wall-clock** ceiling covering a whole worker turn including all of its model and tool calls, enforced in `run_worker()` (#19), which is the single choke point all five workers already pass through. Normal turns finish under 40s, so it only catches the pathological ones. `LLM_RESPONSE_TIMEOUT_SECONDS` is now also passed to the client itself in `llm/clients.py`, so it applies on both routes to the model rather than only the invoker's. And `_invoke_once` now uses the shared `run_with_deadline()` (#18) instead of an executor context manager; verified `ok=False kind=LLMErrorKind.TIMEOUT after 2.0s` where it previously took 60. |
| **Prevention** | **A timeout is only meaningful with its unit named.** "150 seconds" said nothing about *150 seconds of what*, and the answer — idle time between reads — is the one quantity that does not bound a slow generation. Any limit the orchestrator places on an agent needs to state whether it bounds silence, wall-clock duration, or consumed budget, because a coding-agent CLI streaming reasoning tokens is precisely a process that is never idle and may still be making no progress. This lands directly on `maestro delegate --timeout`, documented as a *stale-stream* timeout ("force-terminate the CLI after this much silence") — the same blind spot, in the tool this project delegates through, so the dispatcher needs its own wall-clock deadline over the subprocess regardless. Second: **enforce a limit on every path to the resource, or it is not enforced.** The invoker owned the timeout and workers bypassed the invoker; the same asymmetry let #19 through, and the same shape will recur the moment the orchestrator can reach an agent by more than one route. |

## 18. The run prints its summary and the process never exits — `shutdown(wait=False)` does not opt out of the executor's atexit hook

| Field | Detail |
|---|---|
| **Symptom** | `Run finished \| steps=7 \| documents=['outline.txt']` at 13:54:51, and thirteen minutes later the shell had still not returned a prompt. Nothing was logged after the final banner. Indistinguishable, from the terminal, from a pipeline still working. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/`, CPython 3.12.10 on Windows. Two `note_taker` turns had been abandoned by #17's deadline earlier in the same run. |
| **Diagnosis** | **Established by reproducing it in five lines, outside the project.** `concurrent.futures.thread` registers an `atexit` hook that joins every worker thread it has created, and those threads are **not** daemons; `shutdown(wait=False, cancel_futures=True)` cancels *queued* futures and does not opt out of that hook. So every turn abandoned by the deadline left a thread blocked in a socket read, and the interpreter refused to exit until the server finally answered. The reproduction — submit a 30s sleep, `shutdown(wait=False)`, print, exit — printed and then hung, killed at 12s with exit code 124. The interaction is the sharp part: #17's fix *created* this, because before the deadline existed nothing was ever abandoned. |
| **Resolution** | **Fixed.** `run_with_deadline(fn, *, timeout, name)` in `llm/invoker.py` runs the call on a **daemon** thread, which is neither registered with that hook nor joined at shutdown. Both timeout paths — the worker deadline and `_invoke_once` — now share it, which also removed the duplicated thread plumbing. `contextvars.copy_context()` is used so records logged from the thread keep the run's correlation id, and a dedicated `DeadlineExceededError` is raised rather than the builtin `TimeoutError`, documented as "never raised by a provider, so catching it cannot swallow a real transport timeout." Verified end to end: deadline fires on time, normal and error paths unchanged, request id propagates, and the process exits 0 with a worker still mid-`sleep(120)`. |
| **Prevention** | Two, and the second is the one that generalizes. **Nothing in CPython can cancel a thread blocked on a socket read** — the only decision available is whether that thread outlives the process, and `daemon=True` is how you make the answer no. Abandoning work therefore has a cost that must be chosen deliberately: here it is one idle thread and one server slot until the response lands, which is strictly cheaper than paying the deadline twice. And **a cleanup API's name is not its contract**: `wait=False` reads as "do not wait" and the waiting happens somewhere else entirely, at interpreter shutdown, in a hook the calling code never mentions. For the orchestrator, which will abandon agent subprocesses by design, the equivalent question is what a killed adapter leaves behind — an orphaned CLI process holding a worktree lock is this bug with a worse blast radius, and `Architecture.md`'s orphan-reconciliation requirement (ADR-005) is the same argument at process scope. |

## 19. One worker's provider error aborts the whole graph and discards every finished team's work

| Field | Detail |
|---|---|
| **Symptom** | `openai.UnprocessableEntityError: 422` raised out of `doc_writer_agent.invoke()`, through `writing.py:51`, through `orchestrator.py:81`, through `super_graph.stream()`, out of `main.py`, and off the end of the process — a ~90-line traceback ending the run. The research team had already completed successfully and `write_document -> research_results.txt (1459 chars)` had already succeeded nine seconds earlier. Both were lost. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/`, `langchain.agents.create_agent`, local TGI. |
| **Diagnosis** | **Established, and it is a structural gap rather than a missing `try`.** `llm/invoker.py` carries a full error taxonomy — `LLMErrorKind`, retry policy, the FIFO gate, and explicit handling for `UnprocessableEntityError` — and **no worker turn ever reaches it**. `create_agent` calls `model_.invoke()` directly inside LangChain's factory, so the invoker sits on the supervisor path only, and everything it knows about provider failures was inapplicable to the five agents doing the actual work. A small model on a constrained decoder produces those failures routinely (#16), so this was not a rare path. The blast radius is what makes it serious: LangGraph propagates the exception up through every enclosing graph, so one bad generation in one worker discarded the completed output of every team that had already finished. |
| **Resolution** | **Fixed.** `run_worker(agent, name, state)` in `teams/supervisor.py`, which all five worker nodes now route through, and which **always returns a report**: on a deadline miss (#17), `"Worker 'X' ran past its 180s deadline and produced no report. Anything it saved before then is still on disk."`; on any exception, `"Worker 'X' failed with <Type> and produced no report… Detail: <first 300 chars>"`. The truncation is deliberate — a provider error quotes the entire rejected generation, so the raw string was 3000+ characters of backslashes; the report is 440. The full traceback still goes to the log at ERROR. Each node also shed four lines of duplicated logging. Verified against a real 422 and against a hanging call. |
| **Prevention** | The sentence this entry exists for: **a supervisor can route around a worker that failed; it cannot route around a traceback.** Converting an exception into a report is not error-swallowing — it is what makes the failure *routable*, and it preserves the property that matters most, which is that work already on disk survives. Two constraints on doing it correctly, both learned here. The report must say **what state it leaves behind** ("anything it saved before failing is still on disk"), because the next decision depends on that and nothing else can supply it. And the boundary must be at a **choke point**, not per call site: five nodes were each about to grow their own `try`, and the reason there is now one function is the same reason ADR-010 put the wire-format shim on the transport. For the orchestrator this is the agent adapter's contract — an adapter returns a classified outcome and never raises past the router, or a single vendor's bad day costs every worktree in flight. |

## 20. The document tools let the model's habits reach disk: escaped newlines written verbatim, and the note taker claiming the deliverable's file name

| Field | Detail |
|---|---|
| **Symptom** | Two defects, both visible in produced artefacts rather than in any error. (a) `temp/research_results.txt` contained the two characters `\` and `n` everywhere a line break belonged — 3 literal `\n`, 0 real newlines. (b) At 13:13:13 `create_outline -> research_results.txt (4 points)`: the note taker wrote its outline **over the deliverable's file name**, and since `doc_writer` had not run yet, the run's only artefact was a 4-point outline sitting where a document was requested. |
| **Date** | 2026-08-06 |
| **Environment** | `yt_tutorial/tools/documents.py`, local TGI with grammar-constrained tool arguments, `llama-3.1-8b-instruct`. |
| **Diagnosis** | **Established, two unrelated causes sharing one property — the model's output reaches disk unmediated.** (a) The model writes a line break inside a JSON tool argument as the two characters `\` and `n`, and this server's constrained decoder hands them over **verbatim** rather than unescaping them; the same habit unbounded is #16's runaway backslash run, so the two are the mild and severe forms of one behaviour. (b) The note taker aims at `research_results.txt` because **it is the only file name anywhere in its context** — the #15 fix that passes the full conversation into a team is what put the user's request, naming that file, in front of it. `NOTE_TAKER_AGENT` had a prompt rule forbidding exactly this, and the rule lost; worse, the negative phrasing ("NEVER write it to the file name the user asked for…") had already been observed being echoed *into an outline file as an outline point* in an earlier run. |
| **Resolution** | **Fixed, both structurally.** (a) `_unescape()` converts `\n`/`\t` escape runs to real characters and collapses bare backslash runs to a newline, applied in `write_document`, `create_outline`, and `edit_document`. A lone backslash before a non-escape letter is left alone, so `C:\Users` and `50%` survive; verified against the real damaged file (3 literal `\n` → 0, 0 real newlines → 4) and against a 40-backslash run. (b) Two guards on `create_outline`, ordered **name-first**: a name guard rejecting any file name not recognisable as an outline's, and a content guard refusing to overwrite a file that already holds a document. The ordering is the load-bearing part — when the note taker runs *before* the writer the deliverable does not exist yet, so the content guard has nothing to protect and only the name check stands between the outline and the deliverable's name. Both errors are self-correcting (the model reads them and calls `outline.txt`), regenerating an outline over an outline is still allowed, and `write_document` is untouched. The prompt rule was also flipped from a prohibition to a positive instruction naming `outline.txt`. |
| **Prevention** | **A prompt rule competing against a fact in the request loses.** The request names one file; the system prompt names none and merely forbids one — on an 8B model that is not a close contest, and the fix has to be a constraint the tool enforces rather than a rule the model must remember. This is ADR-011's argument arriving from outside termination, and it generalizes: where a model's own context supplies a strong default, only the tool boundary can override it. Two smaller notes. A guard that only fires against *existing* state has a startup hole — the content guard was written first, was correct, and was useless in the ordering that actually occurred; **check the intent, not just the collision.** And an escaping convention is part of the wire contract: `_unescape` belongs at the tool boundary for the same reason `tgi_compat` belongs on the transport (ADR-010), because asking the model to escape correctly on a decoder that will not let it is not a fix. |
