## 1. Cross-agent context transfer: what can and can't move between coding-agent CLIs

| Field | Detail |
|---|---|
| **Topic** | Whether "session context" can literally move between Claude Code, Codex, Gemini CLI, and similar tools when an orchestrator hands a task from one to another |
| **Date** | 2026-07-31 |
| **Findings** | A model's internal session state (KV cache, hidden activations, provider-side conversation state) cannot be transferred across vendors — there is no API that exposes or accepts it. What *can* be carried forward: (1) each CLI's own native resumable session ID, useful only for resuming with the *same* vendor later; (2) structured handoff summaries written by the outgoing agent; (3) shared Git state (diffs, commits, branches, worktrees); (4) a canonical task record (objective, requirements, decisions, completed/remaining work, failed attempts); (5) event/transcript history stored by the orchestrator itself, not by any vendor. |
| **Conclusion** | Any orchestrator design must explicitly build and pass a context packet at every handoff rather than assuming continuity. Native session IDs are an optimization for same-agent resumption, not a cross-vendor continuity mechanism. This is now a hard requirement in the project checklist ("does not falsely claim to transfer hidden token-level state between vendors") and shapes the canonical task-context schema in [[001-skill-distribution-and-explicit-injection]]-adjacent design work. |
| **Relevance to Project** | Governs the design of the canonical task context object and the "Handoff Builder" component described in `Architecture.md`. Also the reason a "Session Registry" (per-agent native session IDs) is a separate concern from the canonical task context. |

## 4. LangGraph as the routing/supervisor layer over CLI-based coding agents

| Field | Detail |
|---|---|
| **Topic** | How to integrate CLI-based coding agents (Claude Code, Codex) as nodes in an existing LangGraph `StateGraph`, and how to distribute a shared skill (e.g., a `graphify`-style SKILL.md) to multiple agent CLIs consistently |
| **Date** | 2026-07-31 |
| **Findings** | A LangGraph node can wrap a CLI call directly: shell out via `subprocess.run([...])` with a headless/non-interactive flag (`claude -p ... --output-format json`, `codex exec ... --json`), parse the JSON result, and return it as graph state exactly like an LLM-calling node would (`(state) -> dict`). GitHub Copilot has no scriptable agentic-loop CLI equivalent to Claude Code/Codex, so it's better modeled as a tool call inside a node (parse `gh copilot suggest` output and feed it back into state) rather than as its own graph node that owns a task end-to-end. For shared skills: Claude Code auto-discovers `.claude/skills/`, Codex has no equivalent and instead reads `AGENTS.md`; the reliable pattern is one canonical `skills/<name>/SKILL.md`, referenced by a symlink for Claude Code and a pointer line in `AGENTS.md` for Codex — but auto-discovery should not be trusted for headless/one-shot subprocess calls, since there is no visibility into whether it fired. The robust approach is to read the skill file and inject its contents directly into the constructed prompt string before the subprocess call, for every agent, every time. |
| **Conclusion** | Skill distribution to CLI-based agents in this project should default to explicit injection at prompt-construction time, with the symlink/`AGENTS.md` convention kept only as a fallback for humans running an agent interactively outside the orchestrator. See ADR-001. |
| **Relevance to Project** | Directly shapes the design of both the "Agent Router" nodes and the "Handoff Builder" in `Architecture.md`, and the decision recorded in ADR-001. |

## 5. OpenHands Agent Canvas vs. Claw Orchestrator — what each actually provides beneath custom orchestration logic

| Field | Detail |
|---|---|
| **Topic** | Following ADR-003, a deeper comparison of the two execution-layer candidates, specifically: given that the project's distinctive features must be hand-built either way, what does each platform actually save? |
| **Date** | 2026-08-03 |
| **Findings** | An earlier assessment (topic 3) understated OpenHands: it *does* provide persistent conversation storage (messages, events, files, task state, provided the backend storage/volume is persisted) and *does* provide multi-engine access to Claude Code, Codex, Gemini CLI, and other agents via Agent Client Protocol (ACP). The real difference is one of abstraction, not feature count. **Claw Orchestrator's** primary abstraction is a coordinated *group* of external coding-agent sessions: it ships fan-out, mixed-agent councils, consensus rounds, and Planner→Coder→Reviewer loops, with Git worktrees and branches integrated into those Council workflows, plus direct fine-grained control over supported coding CLIs and their sessions. **OpenHands'** primary abstraction is a complete *environment* in which development agents run: secure sandboxes, file editing and shell execution, repository integration, event streaming, Docker/VM/Kubernetes/local/remote execution backends, secrets handling, a monitoring UI, its own software-development agent, and scheduled/event-driven automations. Neither implements the project's headline behaviour — monitor an agent's remaining allowance, detect exhaustion or an unexpected stop, select a replacement, build a handoff, resume, and loop until deterministic checks pass. Also clarified: switching an LLM profile mid-conversation (which OpenHands supports while preserving history) is *not* the same as switching a coding-agent runtime — Claude Code → Codex is a change of agent process, not a change of model. |
| **Conclusion** | Neither platform reduces the custom work; they differ only in which surrounding layer you inherit. Claw is the better fit if multi-agent coordination primitives and direct CLI session control are the foundation you want; OpenHands is better if sandbox infrastructure, UI, integrations, and deployment management are worth more than coordination primitives. Critically, if the orchestration logic is built in a workflow layer anyway and Claw's Council/fan-out/Autoloop/worktree features go unused, Claw's advantage collapses to near zero — which reframes the question as "do we need an execution *platform* at all, or just a process supervisor?" A hands-on OpenHands trial was attempted the same day to settle this empirically; it was blocked by a connection failure to the local LLM endpoint before any agent work ran (see `Bugs.md` #1). |
| **Relevance to Project** | Resolves the ADR-003 comparison in principle without selecting either tool — and, together with topic 8, is why the execution layer ultimately went to neither (see ADR-004). |

## 6. Per-agent budget limits are not queryable — consequences for the routing model

| Field | Detail |
|---|---|
| **Topic** | The project routes work by "token budget of each coding agent." Whether that quantity actually exists and can be read at runtime. |
| **Date** | 2026-08-03 |
| **Findings** | None of the four intended agents exposes "tokens remaining" as a readable value, and their limits are not even the same *kind* of quantity. Claude Code is bounded by rolling usage windows on a subscription, or $/token on an API key; usage is reported per call but remaining headroom is not exposed. Codex is bounded by rate-limit windows on a ChatGPT plan, or $/token on an API key; also not queryable. Gemini CLI's free tier is bounded by **request count** (per-minute and per-day), not tokens at all. DeepSeek is pure $/token with only an account balance readable. Separately: DeepSeek is a *model*, not an agentic coding CLI in the class of Claude Code or Codex — using it as a first-class coding agent requires pairing it with a harness that accepts a custom OpenAI-compatible endpoint (Aider, OpenCode, or similar), otherwise it is limited to non-agentic roles (reviewer, planner, summarizer) served by a plain API call. |
| **Conclusion** | "Remaining tokens" cannot be modelled directly. The workable substitute is a normalized per-agent ledger with a `limit_type` (rolling window / daily requests / monetary / none), user-configured limits, consumption accumulated from each call's reported usage, and a state field (available / degraded / exhausted / cooldown). It must be updated from two sources with an explicit precedence: proactive accumulation is an *estimate* used for pre-emptive routing, while a non-zero exit plus a rate-limit message is the *authoritative* signal that triggers failover and a cooldown. Vendor error strings should live in configuration rather than code, since they get reworded. Two corollaries: reserve headroom before dispatching (a mid-task death costs both the partial work and a cold-start handoff), and price agent-switching into the routing decision, since returning to an agent with a live native session is far cheaper than cold-starting a different vendor. |
| **Relevance to Project** | Constrains the "Agent Router" in `Architecture.md`: routing is necessarily best-effort estimation with a reactive override, not budget arithmetic. Also determines DeepSeek's role, which remains unresolved pending a hands-on check of which harness it runs under. |

## 7. Workflow-engine layer — Langflow, LangGraph, Temporal, or hand-rolled

| Field | Detail |
|---|---|
| **Topic** | Which layer should own workflow state, routing, retries, cycles, and crash recovery — re-examined after a provisional stack table named Langflow while ADR-002 had chosen LangGraph |
| **Date** | 2026-08-03 |
| **Findings** | Langflow and LangGraph are not interchangeable. Langflow is a visual drag-and-drop builder over LangChain — good for prototyping and for showing a flow diagram to someone. LangGraph is a durable state-machine runtime with cycles, conditional edges, checkpointers, interrupts, and resume-from-checkpoint. What this project needs from that layer — fix→recheck cycles, conditional routing on agent state, checkpoint/resume after a crash, mid-run interruption, and nodes that block for minutes on a subprocess — is LangGraph's feature list, not Langflow's; and once every node is custom Python wrapping a subprocess, the visual surface stops paying for itself. Temporal was also reviewed as the durable-execution option in this slot (workflow durability, retries, timeouts, and recovery as first-class primitives, at the cost of running a server and adopting its worker/determinism model); the detailed evaluation notes for it were not captured in the session transcripts and should be recorded here when available. A third option was raised: for a first version the described workflow is a linear pipeline with a retry loop — roughly a couple hundred lines of plain Python over a persisted state document — and the genuinely hard parts (the agent adapter layer, the handoff packet, the budget ledger) get no help from any of these engines. |
| **Conclusion** | Langflow is not the right choice for the runtime; if a visual surface is wanted it belongs on top as an authoring/monitoring UI, not as the engine. Between LangGraph and Temporal, the choice can be deferred: adopting a workflow framework before the adapter/handoff/ledger layers exist risks encoding the wrong shape. This question was ultimately overtaken by the Maestro decision (topic 8, ADR-004), which supplies its own run/step lifecycle — but it remains live for whatever executes *inside* that lifecycle. |
| **Relevance to Project** | Directly amends ADR-002's LangGraph choice and removes Langflow from the stack table in `Architecture.md`. |

## 8. Maestro-flow (Ralph) and Flow-next as mid-task cross-agent delegation frameworks

| Field | Detail |
|---|---|
| **Topic** | Two Claude Code-native orchestration frameworks surfaced late in the search, evaluated for whether they perform mid-task switching between different coding-agent CLIs |
| **Date** | 2026-08-03 |
| **Findings** | **Maestro-flow / Ralph** defines three node types in a chain, and the distinction is the important part: `skill` nodes run synchronously as a command execution in the host CLI; `cli` nodes run via `maestro delegate` as a *background CLI delegate execution* — this is the agent-switching mechanism, and it is architectural rather than bolted on; `decision` nodes re-evaluate results and decide whether to continue or insert a fix loop. A chain is therefore not locked to a single agent: individual steps typed `cli` hand off to a different backend CLI while the session continues. Its default lifecycle is plan → execute → verify → ✓post-verify → business-test → ✓post-business-test → review → ✓post-review → test-gen + test, where ✓ marks a decision gate; `--quality quick` collapses this to verify → CLI-review, and that CLI-review stage is a `cli` node, i.e. an actual delegate call to another agent. Its five built-in decision gates are all post-execution (post-verify, post-review, post-test, post-milestone) — there is no built-in gate that reviews a *plan* before execution begins, so a plan-review checkpoint has to be assembled manually with `maestro delegate`. **Flow-next** exposes the same two checkpoints as named, first-class commands (`plan-review`, `impl-review`) with a configured backend from setup, and is broadly configurable: `flowctl config set review.backend codex|repoprompt|copilot|cursor` swaps the reviewer; `work.delegate=codex` (off by default, consent-gated) offloads implementation itself; per-task reviewer routing lets one epic route different tasks to different reviewers; review granularity is selectable per-task or per-epic; optional stages (interview, qa, spec-completion-review) can be switched on; and the same gates run under three autonomy levels — manual, `pilot` (one stage per tick), or a fully autonomous Ralph loop. It is first-class on Claude Code, Codex, and Factory Droid, so even the host CLI driving the orchestration can be swapped. |
| **Conclusion** | Both frameworks demonstrate that mid-task delegation to a *different* coding-agent CLI is a solved primitive — `maestro delegate` and `flowctl`-routed review backends do concretely what the earlier survey found missing from every candidate. Flow-next is the more configurable of the two out of the box, particularly for pre-execution plan review, which Ralph requires hand-assembly for. Maestro was nevertheless selected (ADR-004) on the strength of its delegate primitive, run/step lifecycle, and persistent knowledge system, and because it is already installed and configured in this environment. |
| **Relevance to Project** | Supplies the execution/session layer that ADR-002 and ADR-003 left unresolved, and retires the Claw-vs-OpenHands question. See ADR-004. |

## 9. Multi-agent collaboration structures, and what the hierarchical supervisor pattern maps onto here

| Field | Detail |
|---|---|
| **Topic** | Multi-agent system structures in general, and the hierarchical supervisor pattern specifically — learned from a 52-minute LangGraph walkthrough and then implemented (ADR-008) |
| **Date** | 2026-08-04 |
| **Findings** | Multi-agent collaboration is classified along three axes: **type** (cooperative vs. competitive), **structure** (centralized, distributed, hierarchical), and **strategy** (rule-based, model-based, role-based). The structural taxonomy is the useful one here, and it is an ordered progression rather than a menu. A **network** structure lets any agent hand control to any other; with no defined roles this degenerates into chaos. A **supervisor** structure puts one agent in charge of routing to all workers — controlled, but a single point of failure. **Supervisor-as-tool** is a variation where workers are exposed to the supervisor as tool calls rather than as agents. A **hierarchical** structure nests supervisors: a top supervisor routes to team supervisors, each of which routes to its own workers — organizationally, a CEO over team leads over specialists. The mechanical primitive underneath all of them in LangGraph is `Command(goto=<target>, update=<state patch>)`, which the documentation calls a *handoff*: it names a destination and carries a payload in one object. Two implementation details are load-bearing and easy to miss. Routing targets are declared by the node function's **return type annotation** — `Command[Literal["supervisor"]]` on a worker, `Command[Literal[*members, END]]` on a supervisor — and LangGraph derives graph edges from those annotations, so a `goto` value that does not appear in the corresponding `Literal` produces a validation error at compile time rather than a routing failure at run time. And the supervisor must emit **structured output** (a `Router` TypedDict with a `next` field constrained to the member names plus `FINISH`), not free text, because its entire job is choosing one of a small closed set. |
| **Conclusion** | The hierarchical supervisor pattern is a close structural match for this project's planner → implementer → reviewer → fixer workflow, but the correspondence is at the level of *shape*, not implementation. Every mapping holds — supervisor → Agent Router, `Command(goto=..., update=...)` → handoff packet, graph state → Canonical Task Context Store, worker node → agent adapter, `FINISH` → deterministic check pass — with one decisive difference: in the tutorial the workers are LLM agents constructed *inside* one Python process and sharing its memory, whereas here they are separate vendor CLI processes that can be killed mid-sentence by a rate limit. Everything ADR-005 exists to handle — reconstructing state after a hard kill rather than receiving it from a cooperative exit — is precisely what an in-process `Command` handoff never has to solve. The supervisor's single-point-of-failure property also carries over directly and is worse here: this project's router holds the budget ledger, so its own crash strands every in-flight worktree. |
| **Relevance to Project** | Confirms the shape of the "Agent Router" and "Handoff Builder" in `Architecture.md` while sharpening why they cannot be a thin wrapper over a graph framework's handoff primitive. Also supplies hands-on input to topic 7's deferred workflow-engine choice: LangGraph's `Command`/`Literal` edge inference is ergonomic for in-process routing and says nothing about durability across process death, which is the axis that actually decides that question. |

## 10. Tutorial material drifts from installed LangGraph/LangChain 1.x APIs

| Field | Detail |
|---|---|
| **Topic** | The gap between multi-agent tutorial code and the currently installed `langgraph` 1.2.10 / `langchain` 1.3.14 APIs, and how it manifests |
| **Date** | 2026-08-04 |
| **Findings** | Six errors were hit getting a compiling graph standing, and only one was a genuine typo — the rest were API drift, each surfacing as a different and mostly unhelpful failure. `create_react_agent` from `langgraph.prebuilt` is superseded by **`create_agent` from `langchain.agents`**; the tutorial's version still exists but is not the current path. The end sentinel must be the **exported `END` constant**, not a hand-written string — `'_end_'` is accepted as an ordinary node name and fails later as `ValueError: Found edge ending at unknown node`, pointing at the edge rather than at the string that caused it. `GraphState` is not a LangGraph export at all (the builder is `StateGraph`; the state type is user-defined, typically subclassing `MessagesState`). `draw_mermaid_png()` requires **no** `mermaid` PyPI package — and the package by that name is unusable anyway, since its metadata declares a malformed dependency (`torch (>=1.7torchvision)`) that no resolver will accept; the Mermaid CLI, if genuinely needed, is an npm package. A missing `return supervisor` at the end of the node factory surfaced as a **bare `RuntimeError` with no message** from `add_node`, because the node argument was `None` — the error names neither the node nor the cause. |
| **Conclusion** | Tutorial code for this ecosystem should be treated as a source of *architecture*, not of *API*: take the structure and the reasoning, then translate every import and constructor against the installed version. The failure modes deserve specific wariness, because two of the six pointed at the wrong place entirely (the `_end_` string reported as an edge error; the missing `return` reported as a contentless `RuntimeError`) and one — reaching for a same-named PyPI package to satisfy a rendering call that needed nothing — was a wrong assumption rather than a wrong API. |
| **Relevance to Project** | Direct caution for the Build Guide's Stage 11 workflow-engine decision (`Research.md` topic 7): a framework whose API surface moves this quickly is a different kind of commitment from one that does not, and any adoption should be dated and pinned. Also a caution for the orchestrator generally, since agent CLIs reword their own outputs the same way — which is exactly why ADR-006 puts vendor rate-limit error strings in configuration rather than in code. |

## 11. RAG-work's `llm_caller.py` as a working prototype of ADR-006's reactive detection

| Field | Detail |
|---|---|
| **Topic** | What the LLM rate-limit machinery ported from `RAG-work` (ADR-009) already implements, and how much of it transfers to the agent-CLI budget ledger |
| **Date** | 2026-08-04 |
| **Findings** | `llm_caller.py` (926 lines) implements several mechanisms that ADR-006 specifies in the abstract, at the LLM-API boundary rather than the agent-process boundary. A **FIFO call gate** built from a queue of per-thread events enforces strict arrival-order fairness, so concurrent callers cannot stampede a shared limit. A thread that receives a 429 **does not re-enqueue** — it holds the gate, sleeps the reset window, and retries from the front, which prevents a rate-limited caller from being starved behind newer arrivals. A **global token-reset deadline** (`_token_reset_until`, monotonic) is written by whichever thread first sees a 429 and read by whoever holds the gate, so the reset window is paid *exactly once per exhaustion event* rather than once per waiting thread. An **adaptive inter-call cooldown** computes a floor as `(1 - remaining/limit) × reset_window` from rate-limit response headers, then doubles it after a recovered 429 and halves it after three consecutive clean first-attempt successes. Failures are classified into a closed `LLMErrorKind` enum (rate limit, auth, connection, timeout, server error, and so on) across both `groq.*` and `openai.*` exception classes, plus raw `httpx`/`requests` failures, and a `LLMRateLimitAbortError` fires when cumulative delay would exceed a configured ceiling. |
| **Conclusion** | Three things transfer to the budget ledger essentially unchanged in concept: exhaustion detected reactively from a classified failure rather than from an estimate; the cooldown-with-shared-deadline so a limit is waited out once rather than per-consumer; and an abort threshold so waiting cannot exceed the value of the work. Two things do not transfer. The **signal source** is different in kind — HTTP 429 responses with structured `x-ratelimit-*` headers versus a *process exit code plus a message string* from a coding-agent CLI, which is why ADR-006 puts those strings in configuration. And the **unit of loss** is different: a failed LLM call can simply be retried, whereas a killed coding agent leaves a half-finished worktree, which is the entire reason ADR-005's reconstruction-on-entry exists and has no analogue here. The adaptive-cooldown *formula* also does not transfer, since it presumes a readable remaining/limit pair — exactly the value topic 6 established no coding-agent vendor exposes. |
| **Relevance to Project** | Makes ADR-006's "reactive signal is authoritative" concrete: there is a working reference implementation of the pattern one layer down, and its FIFO gate is directly reusable for the workspace lock (one active agent per worktree) that `Architecture.md`'s 2026-08-03 changelog names as non-optional. It also marks the boundary — the ledger is not a port of this module, because the quantity it measures is not readable and the failure it absorbs is not idempotent. |

## 12. "OpenAI-compatible" is a claim about requests, not a contract about responses — a measured capability matrix for TGI 3.0

| Field | Detail |
|---|---|
| **Topic** | What an OpenAI-compatible endpoint actually guarantees, established by probing a local HuggingFace TGI 3.0 server rather than by reading either side's documentation |
| **Date** | 2026-08-05 |
| **Findings** | Four request shapes were sent to `/v1/chat/completions` on TGI `3.0.0-sha-8f326c9`, identical but for how structured output was requested: plain chat **200**; `response_format: {"type": "json_object"}` **500**; `response_format: {"type": "json_schema", …}` **500**; `tools: […]` **200**, with `tool_choice` both `auto` and forced returning well-formed calls that respect the parameter `enum`. `json_schema` is what `langchain-openai` 1.4.1 sends by default from `with_structured_output()`, so the library's default path is the one route this server does not implement. Deviations in the *responses* were more numerous and less discoverable: tool-call `arguments` returned as a JSON object where the OpenAI API returns a string; `content` omitted entirely on tool-call turns; every tool call labelled `id: "0"`; and a non-spec `"description": null` inside the function object. One deviation is on the request side and only appears on a second turn: TGI answers **500** for any assistant message with `content: null`, which is precisely what langchain re-serializes an empty content field into. Bisected with five message shapes differing only in that field — 200/200/200/**500**/200 (`Bugs.md` #7, #8). Two behavioural properties round out the picture: TGI **grammar-constrains** generation to the attached tool schemas, which is why an 8B model emits reliably valid tool JSON (topic 13 covers what that costs), and its responses carry **no usage figures** the client could read, so token accounting against this endpoint is unavailable entirely. |
| **Conclusion** | Compatibility is per-feature, directional, and only knowable by measurement. A useful decomposition is four separate questions — does it accept the request schema, does it return the response schema, does it implement the optional feature, and does it report the metadata — and this server answers yes, no, partly, and no. Two practical rules follow. Absorb wire-format divergence at the **transport boundary**, once, rather than at the call sites that happen to hit it (ADR-010): the first fix attempt here patched the supervisor and would have left all five worker agents broken one turn later. And keep negotiable *capability* choices in configuration keyed to the deployment (`STRUCTURED_OUTPUT_METHOD`), distinct from the shim, since they are legitimate client choices rather than defects. Client-library defaults deserve specific suspicion: nothing in the calling code named `json_schema`, which made it the least visible coupling in the stack. |
| **Relevance to Project** | Bears directly on ADR-006's unresolved DeepSeek question, which proposes pairing it with "a harness that accepts a custom OpenAI-compatible endpoint" — this topic says that phrase needs decomposing into a capability matrix before an adapter can rely on any of it. More broadly it is the first hands-on evidence for how the Stage 4 **agent adapter** layer should be shaped: each vendor's quirks normalize inside its adapter, never in the router or the workflow code downstream. The absent usage figures also sharpen topic 6 and topic 11 — against this endpoint, not only is the *remaining* allowance unreadable, the *consumed* amount is too, so both halves of a ledger built on this shape would be inert (`Bugs.md` #6a). |

## 13. Termination in a small-model agent loop is a structural property, not a promptable one

| Field | Detail |
|---|---|
| **Topic** | Why the hierarchical supervisor graph would not stop, established across four consecutive non-terminating runs, and what actually ends an agent loop |
| **Date** | 2026-08-05 |
| **Findings** | The decisive evidence is a controlled A/B against the live server: the same four-message conversation was sent twice, differing **only** in whether `tools` was present in the request. With `tools` the model returned another tool call and empty content; without it, a complete, well-formed final answer as ordinary text. TGI grammar-constrains generation to the attached tool schemas, so while tools are bound the model **structurally cannot** produce the assistant-turn-with-content-and-no-tool-calls that a ReAct loop exits on. This is a property of the serving stack, not a defect in the agent code, and it means the loop had no reachable exit. Two prompt-level remedies were tried and observed to fail: an explicit `finish_work` tool with a matching instruction produced another `write_document` call, and a supervisor prompt stating which parts of a request its team could not perform was ignored, with the router re-selecting the same worker anyway. What worked was a cap in code at each layer. The instructive part is what happened next: bounding the worker did not end the loop, it **moved** it. `ToolCallLimitMiddleware(exit_behavior="end")` terminates a run with a bookkeeping stub as its final message (`Tool call limit reached: run limit exceeded (4/3 calls)`), that stub became the worker's report to its supervisor, it read as unfinished work, and the supervisor re-routed indefinitely — so a second cap and a report-translation step were both required (`Bugs.md` #9, #13). A third layer sits above these and is not a solution: `recursion_limit` is a super-step budget whose exhaustion is always a crash, so a design relying on it to stop has no termination design at all. |
| **Conclusion** | Three findings generalize past this model. **A safety property cannot rest on the cooperation of the component it constrains** — no wording could have closed a loop the model was prevented from exiting, and two attempts to prove otherwise are on record. **A guard that ends a run leaves its own artefact in the transcript**, and if any downstream consumer reads that artefact as content, the loop relocates rather than closing; whatever ends a run must also state what the run accomplished. And **a bound is a behaviour change, not only a safety property**: the same cap that converts an infinite loop into a bounded run converts it into a silent no-op when the model never routes to the worker that would have done the work (topic 14, `Bugs.md` #15). A bound therefore needs to record *why* it fired, distinguishing "stopped because done" from "stopped because bounded" — the current implementation logs one line for both, which is the defect this conclusion is written to prevent repeating. |
| **Relevance to Project** | This is the deterministic-check-runner argument arriving from the model side rather than the verification side, and it is now backed by a first-hand case in which an agent could not signal completion even in principle — which strengthens ADR-004's constraint that Maestro's own completion signals stay subordinate to exit-code checks. It also reclassifies two items `Architecture.md`'s 2026-08-03 changelog listed as non-optional refinements: the per-step attempt cap and the fix-loop bound are termination *design*, in the same category as the workspace lock, and belong in the Agent Router from the start rather than as hardening added later. Recorded as ADR-011. |

## 15. Nested budgets: an inherited allowance is a shared allowance

| Field | Detail |
|---|---|
| **Topic** | How LangGraph propagates execution budgets into sub-graphs, and what the resulting failure mode says about per-agent budget accounting |
| **Date** | 2026-08-05 |
| **Findings** | `recursion_limit` bounds **super-steps within one invocation**, not nesting depth — nothing recurses, despite the name. The sandbox has three nested levels (orchestrator graph → team graph → ReAct agent graph), and a sub-graph invoked without a config of its own **inherits the parent's**. Setting `{"recursion_limit": 2}` at the entry point therefore produced `GraphRecursionError` raised inside `research_graph.invoke()`, not in the graph whose config set the value: the orchestrator spent both steps reaching the team, and the team inherited an allowance of 2 for a supervisor↔worker cycle needing several. Raising the value moved the same error to the new limit, still raised in the sub-graph. The fix was explicit per-level allocation — a separate config object passed on every sub-graph invocation — so that a team which spins cannot draw down the orchestrator's budget or starve its sibling (`Bugs.md` #12). |
| **Conclusion** | Three properties make this failure mode hard to read, and none is specific to LangGraph. **The level that exhausts a shared budget is not the level that misconfigured it**, so the traceback points away from the cause. **Inheritance is the default and is invisible at the call site** — the sub-graph invocation that inherited a limit of 2 mentioned no limit at all. And a budget consumed by a nested consumer produces *starvation* of a sibling rather than an error attributable to the consumer. Allocation must therefore be explicit at every level that can independently consume, with the default being isolation rather than inheritance. |
| **Relevance to Project** | The miniature form of what ADR-006's ledger exists to prevent, and a useful one because it is cheap to reproduce. When the orchestrator delegates a step to an agent that itself spawns sub-work — which `maestro delegate` does by design, and which the Handoff Builder's own packet consumes budget to assemble (ADR-005) — an unallocated child draws on the parent task's headroom, and the resulting mid-task death surfaces somewhere other than its cause. Two requirements follow for the ledger: budget is **allocated per delegation, not inherited**, and a reservation is recorded at the point of delegation so that consumption is attributable to the delegating step. This also reinforces topic 13's closing note — `recursion_limit` and its analogues are backstops whose exhaustion is a lost run, never a termination mechanism. |

## 17. What a coding-agent CLI brings that a model API does not

| Field | Detail |
|---|---|
| **Topic** | The difference between calling a model and delegating to an agent CLI, catalogued from driving Claude Code and Codex as subprocesses for the first time (ADR-014, ADR-015, `temp_agents/`) |
| **Date** | 2026-08-06 |
| **Findings** | Nine behaviours, none of which have an analogue in an HTTP call to a model, each found by a run failing. **It arrives with its own context.** Both CLIs auto-discover repository conventions from wherever they are standing — `CLAUDE.md`, `AGENTS.md`, project skills, hooks — and act on them: the first Codex run in this repository spent ~40 s running `maestro search` against a knowledge base before touching the one-line file it had been asked to write. Every prompt now carries an explicit "ignore repository conventions" clause. **Its own system prompt competes with yours, and wins on specificity**: Claude Code wrote a chart into its session scratchpad because its own instructions name that directory by absolute path while the role brief said "the workspace directory" (`Bugs.md` #22). **Tools attach asynchronously** — `--mcp-config` servers connect in the background and the first turn is planned without them unless `alwaysLoad` forces the blocking path (`Bugs.md` #21). **The child's diagnostics are captured, not forwarded**: Claude Code keeps an MCP server's stderr for itself, so tool-layer logs vanish across the boundary. **It prompts for permission by default**, with no terminal to answer, so a run sits until its deadline unless permission mode is set. **Argument passing is the platform's problem**: the npm-installed `codex` is a `.cmd` shim, `cmd.exe` re-parses its arguments, and a multi-line prompt arrives truncated at its first newline — the prompt now always goes over stdin. **The real error is at the end of stderr, not the head**: Codex prints workdir, model, sandbox, and feature warnings before doing anything, so a rejected model spent a whole run looking like an empty result. **Model choice is an account entitlement**, not a parameter — naming `gpt-4o` got every run rejected with "not supported when using Codex with a ChatGPT account", so the only reliably valid value is none. **And the final answer needs a designated channel**: `codex exec` streams its reasoning to stdout with no marker around the answer, so it is collected via `--output-last-message`, while Claude Code supplies `--output-format json`. Two things also went *right* and are worth recording: `--tools ""` disables built-ins without touching MCP tools, and `--strict-mcp-config` ignores every MCP server configured elsewhere on the machine — together they leave exactly the tools a run intends, which is the isolation an adapter needs. |
| **Conclusion** | A coding-agent CLI is not a model behind a different transport; it is **a second agent runtime with its own context, tools, defaults, and opinions**, and every one of those competes with the caller's. Three rules follow. **Instructions must be specific enough to win**, because in every conflict observed here the concrete beat the general — an absolute path beat "the workspace directory", a named file in the user's request beat a prompt prohibition (`Bugs.md` #20) — and what the CLI should *ignore* has to be named as explicitly as what it should do. **Isolation is a set of flags that must be found and verified**, not a default: tool surface, MCP scope, permission mode, and working directory are each independently inherited from the user's machine otherwise, which makes runs unreproducible in ways that do not announce themselves. And **the boundary is where the observability holes are** — stderr ordering, captured child logs, and unmarked final answers are all cases where the information exists and does not cross, so an adapter's job includes routing the child's diagnostics into the parent's audit trail. |
| **Relevance to Project** | This is the empirical content of Build Guide **Stage 4**, which `Architecture.md` has so far described only in principle. Every item above is an adapter responsibility, and the list is the first evidence for how much an adapter actually is — ADR-010 established that vendor quirks normalize inside the adapter using one server's *wire format*; this establishes that the same is true of a vendor's *runtime behaviour*, and that the second category is larger and less discoverable. It also bears on ADR-004: these behaviours sit beneath `maestro delegate` too, so delegating through Maestro inherits rather than avoids them — which is the argument for having driven the CLIs directly once before building on top of the layer that hides them. Two findings feed `Architecture.md`'s completion model directly: a rejected model and a truncated prompt each produced a *plausible empty result* rather than an error (`Bugs.md` #23), which is the same signature as `Bugs.md` #15 and #21 and the reason artefact comparison, not self-report, is the acceptance criterion. |

## 18. Running two vendor CLIs concurrently, and what makes a supervisor's verification mean anything

| Field | Detail |
|---|---|
| **Topic** | A deliberately minimal two-agent demo (`yt_tutorial/temp_agents/`): one supervisor, two agents on two different vendor CLIs chosen by config, two files, run at the same time and then checked |
| **Date** | 2026-08-06 |
| **Findings** | The demo is standalone by design — its own prompts, its own directory, sharing nothing with `teams/` or `claude_agents/` — and exists to isolate two mechanics from the graph machinery around them. **Concurrency**: both agents are submitted to a `ThreadPoolExecutor` before either result is collected, which is what makes them overlap; a submit followed by its own `.result()` would serialise them for no reason. Threads rather than processes because each agent is a `subprocess.run` spending its whole life blocked on a pipe, which releases the GIL — the parallelism is in the two child processes, and Python is only waiting. Measured in a run with the backends swapped: `agent_B` finished at 18:29:11 while `agent_A` ran until 18:29:42, against a serial cost of the sum. **Verification**: both target files are deleted before the run starts, so the supervisor's check means something — a file left over from a previous run would pass while this run wrote nothing. That is `Bugs.md` #15's lesson applied preemptively rather than after the fact, and it paid off immediately, since the first Codex run wrote a **0-byte** file that a stale-artefact check would have waved through. The supervisor itself gets `--tools "Read"` and nothing else: the agents own the files, the supervisor only confirms them. Both output files are committed at the byte level — `Hello World!` and `Hi World!`, verified with `xxd` rather than by reading — which is how a UTF-8 BOM was caught that the supervisor's own `Read`-based verdict had approved (`Bugs.md` #23). |
| **Conclusion** | Two things generalize past a hello-world. **A verification step is only as good as the state it starts from**: "the file contains X" answers a different question from "this run produced a file containing X", and the difference is one `unlink(missing_ok=True)` — which is the artefact-level form of ADR-005's orphan-reconciliation requirement, where a restart must distinguish work this run did from work it inherited. **And an LLM reviewer cannot check byte-exactness**: the supervisor read `﻿Hi World!`, understood it, and reported OK, because `Read` transparently strips a BOM. It was not wrong about the content and it could not have been right about the bytes. That is a small, clean instance of why `Architecture.md` insists completion is decided by deterministic checks rather than by a model's judgement — not because the model is unreliable, but because the property being checked is invisible to it. |
| **Relevance to Project** | The parallel-agent case the orchestrator will have by construction once agents run in separate worktrees, reduced to its smallest form. Three properties transfer. Concurrency across vendor CLIs costs a thread each and nothing else, because the work is in the subprocesses — which makes fan-out cheap and puts the real constraint on **budget and workspace locking**, not on the dispatch mechanism (`Research.md` topic 11's FIFO gate is the candidate for the latter). A supervisor that verifies rather than trusts needs the workspace put into a known state first, which the Handoff Builder's reconstruction step must also do. And per-run correlation becomes necessary rather than nice the moment two agents log into one file, which ADR-013 already provides and this run exercised. |

| **Findings** | `codex exec --json` prints one JSON object per line to stdout; the first line on any turn — cold start or resume — is `{"type":"thread.started","thread_id":"<uuid>"}`, unaffected by `--output-last-message` writing to a separate file. `item.completed` events carrying `"type":"error"` are not failures; they are feature/skill warnings (`default_mode_request_user_input`, skills-context-budget truncation) that appear on turns that otherwise succeed, so a parser must not treat their presence as a failure signal. `--ephemeral` means what its help text says — "run without persisting session files to disk" — literally: a turn run under it still returns a `thread_id` in the `--json` stream, but `codex exec resume <that-id>` fails with `Error: thread/resume: thread/resume failed: no rollout found for thread id ... (code -32600)`, confirmed directly. Argument ordering for resume was suspected broken (options placed after the `resume` subcommand) and tested false: `codex exec --cd X --sandbox Y --skip-git-repo-check --output-last-message F resume <id> -` parses and resumes correctly, because `exec`'s own options are consumed by clap before subcommand dispatch, and `resume` has no `--cd`/`--sandbox`/etc. of its own to conflict with. On the Claude side, `--no-session-persistence` behaves as documented — "sessions will not be saved to disk and cannot be resumed" — but a turn run under it still returns a non-empty `session_id` in `--output-format json`, and passing that id to `--resume` fails with `No conversation found with session ID`, confirmed directly with a codeword-recall probe. |
| **Conclusion** | Both CLIs will hand back an identifier that looks like proof of a resumable session regardless of whether persistence was actually enabled for that turn — the identifier's presence is not evidence of resumability on either vendor, and the only way to know is to either read the specific flag's documentation for what it disclaims or attempt an actual resume as a probe. A subcommand's own `--help` (`codex exec resume --help`) is more reliable for argument-ordering questions than reasoning about clap's parsing model from outside. |
| **Relevance to Project** | Directly the evidence behind `Bugs.md` #30, #31, and ADR-021. Establishes a verification pattern worth reusing for any future vendor-CLI capability claim in this project: probe with a codeword-style round trip (set distinguishing state in turn one, ask for it back in turn two under the mechanism being tested) rather than trusting a returned field's mere presence. Also leaves one adjacent surface unaudited: `adapters/maestro.py`'s own `--resume` construction was not tested against this same failure shape and should not be assumed correct until it is. |

## 26. A Windows subprocess deadline can fire and still never return when an npm shim leaves its real child alive

| Field | Detail |
|---|---|
| **Topic** | Why `subprocess.run(timeout=...)` did not bound Codex, Claude, or Maestro wall-clock time on Windows, and what a correct deadline must own |
| **Date** | 2026-08-09 |
| **Findings** | The final log record in two stalled requirements runs was the Codex dispatch, even though both had a 300-second configured deadline. CPython's Windows timeout path explains the silence exactly: `subprocess.run()` kills its immediate `cmd.exe` child, then calls an un-timed `communicate()`; the npm shim's `node.exe` grandchild survives with inherited pipe handles, so the drain never sees EOF. The deadline therefore fired internally but was observationally indistinguishable from no deadline because no result reached the adapter boundary. A direct reproduction using `cmd.exe` around a sleeping child confirmed the process topology. The shared replacement—`Popen`, a new process group, `communicate(timeout)`, then `taskkill /F /T /PID`—returned after about 2.3 seconds under a 2-second limit while preserving normal stdout on the happy path. |
| **Conclusion** | Time bounding is a resource-ownership property, not merely a numeric argument. If descendants can retain pipes, locks, sockets, or files, a deadline that terminates only the immediate process does not bound the operation. |
| **Relevance to Project** | Produced `Bugs.md` #34 and ADR-025, and applies to all three vendor adapters because the vulnerability belongs to the shared Windows npm-shim boundary rather than to Codex specifically. |

## 27. Two coding-agent slots add vendor/model diversity and stable rework ownership; they do not replace the concurrency cap

| Field | Detail |
|---|---|
| **Topic** | What the dual coding-slot change actually changes in wave execution |
| **Date** | 2026-08-09 |
| **Findings** | Before the change, `run_wave()` already submitted every task before collecting results, so up to `MAX_PARALLEL_TASKS` external subprocesses could run concurrently; however, each cloned one `CODING_AGENT` specification. `CODING_AGENT_A` and `CODING_AGENT_B` introduce two independent backend/model choices and alternate tasks by wave-local index. That mapping is deterministic across attempts, so a task's session id returns to the same vendor/model slot during rework. The per-slot environment variables fall back to the legacy shared variables, allowing identical slots without breaking existing configuration. The default A/B pair is Codex CLI default and Claude Sonnet, while the executor cap remains three. |
| **Conclusion** | The new capability is heterogeneous parallel dispatch and stable slot ownership, not a higher thread count by itself. Throughput can improve when vendors have independent capacity or different strengths, but measured throughput still depends on task independence, `MAX_PARALLEL_TASKS`, vendor latency, and merge/review work. |
| **Relevance to Project** | Directly informs ADR-024 and the Architecture wave-dispatch/configuration sections. It also establishes the right future measurement: compare wave duration, failure rate, and rework success by slot rather than claiming speedup from the existence of two names alone. |

## 28. The 2026-08-09 parallel stress run separated shared prompt context from shared durable memory and exposed wave-level rollback granularity

| Field | Detail |
|---|---|
| **Topic** | Operational findings from the Bhai Digital Studio multi-task run (`run-20260809-153711`) and its saved repeatable prompts |
| **Date** | 2026-08-09 |
