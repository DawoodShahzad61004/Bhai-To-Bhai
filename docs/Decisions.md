## ADR-001 · Distribute shared skills to CLI agents via explicit prompt injection, not auto-discovery

| Field | Detail |
|---|---|
| **Decision** | Skills (e.g., a `graphify`-style `SKILL.md`) are stored once in a canonical `skills/<name>/SKILL.md` location and injected verbatim into the constructed prompt string for every headless agent call, rather than relying on each CLI's own auto-discovery mechanism. |
| **Date** | 2026-07-31 |
| **Context** | Claude Code and Codex discover skill/instruction files differently (`.claude/skills/` vs. `AGENTS.md`), and in headless/subprocess mode (`claude -p ...`, `codex exec ...`) there is no way to confirm whether auto-discovery actually fired. See Research topic 4. |

## ADR-005 · Reconstruct the handoff packet on agent entry from durable artifacts; never summarize on agent exit

| Field | Detail |
|---|---|
| **Decision** | The context packet handed to an incoming agent is assembled fresh at entry from artifacts written continuously during the previous run. No design may depend on an outgoing agent producing a handoff summary as its final act. |
| **Date** | 2026-08-03 |
| **Context** | Recorded from the build-guidance work done this session. The project's headline behaviour is "agent A hits its limit, agent B resumes." The intuitive design — agent runs, finishes, writes a handoff summary, next agent reads it — fails at precisely the moment it exists for: an agent killed by a rate limit or a hard stop never reaches "finishes," never writes the summary, and leaves nothing behind. |
| **Options Considered** | (A) Outgoing agent writes a structured handoff summary before exiting — simplest and highest-fidelity when it works, but produces nothing in the exact failure case the feature targets. · (B) Orchestrator summarizes the transcript after the process exits — survives a hard kill, but requires a full transcript to have been persisted anyway, which is most of option (C). · (C) Make four artifacts durable-by-construction during the run and derive the packet from them at entry: worktree commits (agent instructed to commit per logical step, plus an orchestrator-side auto-commit timer, so a killed process still leaves a diff), plan step status persisted as `pending`/`in_progress`/`done`, the agent's event stream persisted as each event arrives rather than at process exit, and the last check result tied to a commit SHA. |
| **Chosen Solution** | (C). |
| **Rationale** | It makes resumption independent of *how* the previous run ended — clean completion, rate limit, timeout, crash, or a closed laptop all produce the same recoverable state. It also removes any dependency on a dying agent behaving correctly under duress. |
| **Impact** | Load-bearing for the "Handoff Builder" and "Canonical Task Context Store" in `Architecture.md`, and the first thing to build. Two consequences follow: the event stream must be written during the run, never buffered to the end, or the failure mode returns; and any run with a start timestamp but no end timestamp is an orphan from a crash, so restart must reconcile plan state against actual Git state rather than assuming an interrupted run did nothing. |

## ADR-006 · Model agent budgets as a configured ledger with reactive limit detection as the authoritative signal

| Field | Detail |
|---|---|
| **Decision** | Represent each agent's allowance as a normalized ledger entry with a user-configured limit and a `limit_type` (rolling window / daily requests / monetary / none), accumulate consumption from per-call reported usage as an *estimate*, and treat a non-zero exit carrying a rate-limit message as the *authoritative* exhaustion signal that sets a cooldown and triggers failover. |
| **Date** | 2026-08-03 |
| **Context** | Recorded from the build-guidance work done this session. The project statement routes work by "token budget of the coding agents," which presumes a readable remaining-tokens value. Research topic 6 established that no target agent exposes one, and that the four agents are not even bounded by the same kind of quantity — Gemini CLI's free tier is request-count limited rather than token limited, and DeepSeek is bounded only by account balance. |
| **Options Considered** | (A) Query remaining budget from each vendor before routing — not possible; no such API exists for any of the four. · (B) Track consumption client-side only and treat the running total as ground truth — drifts, because vendors count tokens in ways that cannot be fully replicated locally, and drift here causes mid-task deaths. · (C) Detect exhaustion purely reactively from process failure — accurate but purely after the fact, so every limit is discovered by losing work to it. · (D) Combine (B) and (C) with an explicit precedence: the estimate drives pre-emptive routing, the reactive signal overrides it and is what the system trusts. |
| **Chosen Solution** | (D). |
| **Rationale** | Preserves the ability to route *before* dispatching a job that will not fit, while ensuring that inevitable estimate drift degrades into a correct failover rather than a wrong routing decision. |
| **Impact** | Defines the "Agent Router" inputs in `Architecture.md`. Three practical consequences: vendor rate-limit exit codes and error strings belong in configuration rather than code, because vendors reword them; the router must reserve headroom before dispatch, since a mid-task death costs both the partial work and a cold-start handoff; and it must price switching in, since returning to an agent that still holds a native session is materially cheaper than cold-starting a different vendor. DeepSeek's place in the ledger remains unresolved — as a model rather than an agentic CLI, it is either wrapped in a harness accepting a custom OpenAI-compatible endpoint or restricted to non-agentic roles, which is a hands-on question. |
| **Status (2026-08-04)** | **Reinforced by a working prior implementation.** `yt-tutorial/llm_caller.py`, ported from `RAG-work` (ADR-009), already implements this ADR's precedence rule one layer down — at the LLM-API boundary rather than the agent-CLI process boundary — with a shared reset deadline, an adaptive cooldown, and a hard abort threshold. See `Research.md` topic 11 for what transfers to the ledger and what does not. |
| **Status (2026-08-05)** | **Both halves shown inert against a real endpoint, silently.** Running that prior implementation against the local TGI server produced no measurement at all: the header-derived cooldown floor is `0.0` on every call (`Bugs.md` #6, now observed 9/9 in one run), and the responses carry no usage figures either, so the *proactive accumulation* half has no data source (`Bugs.md` #6a, `Research.md` topic 12). Neither degradation raised anything above DEBUG, and both runs looked entirely normal. This does not change the decision — it sharpens the "state field" clause: `available` computed from no data must be a distinct, visible ledger state carried on the entry and surfaced in every routing decision that reads it, not a log line emitted once at the point of failure. `Bugs.md` #12 and `Research.md` topic 15 add a second requirement from a different direction: budget is allocated **per delegation, never inherited**, or a nested consumer spends the parent task's headroom and the death surfaces away from its cause. |
| **Status (2026-08-06)** | **First readable consumption in this project, and it arrives from the agent tier rather than the model tier.** Driving the Claude Code CLI under ADR-014 produced exactly the measurement the local endpoint cannot supply: `--output-format json` returns `total_cost_usd`, per-model `modelUsage` with input/output/cache-read/cache-creation token counts, `num_turns`, `session_id`, and `permission_denials` on **every** invocation — so against this agent the ledger's proactive-accumulation half has a real data source, per delegation, with no header parsing. A measured five-step pipeline run cost **$1.05 across 9 calls**; `Research.md` topic 16 records the shape and its limits. Three consequences, none of which change the decision. The estimate/authoritative precedence still holds, because a per-call cost is *consumption*, never *remaining* — Research topic 6's finding is untouched. A `session_id` on every reply is the Session Registry's key arriving for free, which lets switching cost be priced rather than assumed. And the measurement is **per vendor, not per fleet**: Codex reports none of it (`Research.md` topic 17), so a ledger spanning both agents would be populated by measurement for one and by configured estimate for the other — which is exactly the mixed state the `degraded` field exists to make visible, now with a concrete instance instead of a hypothetical one. |

## ADR-007 · Install Maestro repo-locally and scope its Claude Code hooks to this project

| Field | Detail |
|---|---|
| **Decision** | Install `maestro-flow` as a repository-local npm dependency (`node_modules/maestro-flow`) rather than a global one, and move the 14 Maestro Claude Code hooks plus the statusline from `~/.claude/settings.json` into this project's `./.claude/settings.json`, invoking them through `$CLAUDE_PROJECT_DIR/node_modules/.bin/maestro`. Leave `~/.maestro/` in place. |
| **Date** | 2026-08-04 |
| **Context** | Maestro had been installed globally (`npm install -g maestro-flow`), which was not the intent — the dependency belongs to this project. The stated request was to move it into the repo's `uv` environment. Two findings reframed the task. First, `maestro-flow` is an npm package with no PyPI equivalent and `uv` manages Python only; the repo's `.venv` also had no `pyproject.toml` or `uv.lock`, so it was a bare venv rather than a uv project. There is no version of this change that `uv` can express. Second, what made Maestro *global* in practice was not the binary on `PATH` but 14 hooks and a statusline registered in `~/.claude/settings.json`, which ran in **every** project opened on this machine — and which had already created stray `.workflow/` cache directories in this repo and in the unrelated sibling `Resume` project. Binary location and hook scope are independent decisions. |
| **Options Considered** | (A) Leave the global install alone — zero work, but the dependency stays unpinned per-project and the hooks keep firing everywhere. · (B) Install locally but leave the hooks global — the binary is scoped, but the 14 hooks would break with `command not found` in every project once the global binary is removed, which is strictly worse than (A). · (C) Install locally **and** migrate the hooks into project scope, so both the binary and the automation are bounded by this repository. · (D) Additionally relocate `~/.maestro/` (config, workflows, templates) into the repo — maximum isolation. |
| **Chosen Solution** | (C). `~/.maestro/` was explicitly excluded, per (D) being rejected. |
| **Rationale** | (C) is the only option that makes the scoping real: the hooks are the part actually felt across projects, and they cannot outlive the global binary they invoke. (D) was rejected because the global `CLAUDE.md` `@`-imports `~/.maestro/cli-tools.json` and `~/.maestro/workflows/delegate-usage.md` on every session in every project; relocating them would break instruction loading well outside this repository's blast radius. Sequencing mattered as much as the choice: the local binary was proven working — version probe, a live `hooks run session-context`, statusline, `search`, `delegate show`, and the literal `$CLAUDE_PROJECT_DIR` command strings — *before* the global package was uninstalled, with the previous global settings backed up to `~/.claude/settings.json.bak-20260804`. |
| **Impact** | `maestro` is no longer resolvable on `PATH`; every invocation, including from orchestrator code, must go through `node_modules/.bin/maestro`. This immediately broke `orchestrator/preflight.py`, which probes a bare `"maestro"` (`Bugs.md` #3), and it generalizes: the Build Guide's Stage 0 preflight and every future adapter must resolve agent executables through an explicit, configurable path rather than assuming `PATH`. Two secondary effects: npm 11 gated 5 native install scripts, so Maestro search runs BM25-only until `npm install-scripts approve` is run; and `.claude/settings.json` is `.gitignore`d, so the migrated hook configuration is **not** tracked in version control and will not follow a fresh clone. |

## ADR-009 · Reuse RAG-work's LLM call plumbing rather than writing fresh equivalents

| Field | Detail |
|---|---|
| **Decision** | Port `llm_caller.py`, `logger_config.py`, `config.py`, and `llm_setup.py` from the sibling `RAG-work` project into `yt-tutorial/` largely unchanged, rather than writing new LLM invocation, logging, and configuration modules for the tutorial track. |
| **Date** | 2026-08-04 |
| **Context** | The tutorial build needs LLM calls that survive rate limits. `RAG-work` already contains a hardened implementation of exactly this, developed across roughly a month of dated sessions: a FIFO call gate with per-thread events for strict arrival-order fairness, a global token-reset deadline so a 429's reset window is paid exactly once per exhaustion event rather than once per waiting thread, an adaptive inter-call cooldown derived from rate-limit response headers, retry/backoff with a hard abort threshold, and an LLM output repair layer. Rebuilding that would be a month of rediscovery for a sandbox. |
| **Options Considered** | (A) Write minimal fresh plumbing — small, fitted to the tutorial, no inherited assumptions, but re-learns every rate-limit lesson `RAG-work` already paid for. · (B) Use LangChain's built-in retry (`max_retries`) and no gate at all — smallest possible, but the tutorial's supervisor pattern issues many short serial LLM calls, which is the exact traffic shape that trips rate limits. · (C) Port the `RAG-work` modules as-is and point them at this project's configured endpoint. · (D) Port them and refactor the vendor-specific parts out first. |
| **Chosen Solution** | (C). |
| **Rationale** | The sandbox's purpose (ADR-008) is learning multi-agent orchestration, not re-deriving rate-limit handling; spending the budget on (D)'s refactor would invert that. `RAG-work`'s modules are also self-contained — `llm_caller.py` depends only on `config.py` and third-party clients — so the port is a copy rather than an integration. |
| **Impact** | Two known costs, both accepted deliberately rather than discovered later. The error taxonomy handles both `groq.*` and `openai.*` exception classes, so classification is vendor-agnostic — but the *adaptive cooldown* derives its floor from Groq's `x-ratelimit-*-tokens` headers captured via an httpx event hook that only attaches to a Groq client, and `llm_setup.py` now configures `ChatOpenAI` against a custom endpoint. The hook silently declines to attach and the cooldown floor degrades to zero (`Bugs.md` #6). Separately, `config.py` carries constants for retrieval and embedding timeouts that have no consumer in this project. Both are acceptable in a sandbox and would need resolving before any of this reaches `orchestrator/`. The larger consequence is architectural rather than incidental: `llm_caller.py` is a working implementation of ADR-006's reactive-detection half, one layer below where the budget ledger needs it — see `Research.md` topic 11. |
| **Status (2026-08-05)** | **Partly superseded, and a third cost found that this ADR had not anticipated.** `logger_config.py` was not merely mis-fitted to this project — it could not run at all: `setup_logging()` raised `NameError` on two handler variables that were never constructed, and half the file imported `app_workflow.*` packages belonging to `RAG-work` (`Bugs.md` #14). It went undetected for a day because nothing imported it, so the port had been validated only by the modules actually in use. It is replaced rather than repaired by ADR-013. The `llm_caller.py` port stands and remains the right call — the distinction that emerged is **port what is expensive to re-derive, rewrite what is cheap**: 926 lines of hard-won rate-limit behaviour versus 265 lines of integration glue for services this project does not run. The general lesson is that a ported module's **transitive imports are part of its contract**, and only executing its entry points in the destination environment establishes that it works; an import-only check would have caught the `app_workflow` half but not the `NameError` inside a function body. |

| Field | Detail |
|---|---|
| **Decision** | Normalize the local TGI server's deviations from the OpenAI wire format in a single `httpx` transport (`yt-tutorial/llm/tgi_compat.py`) installed on the shared HTTP client, rather than working around them at the call sites that encounter them. |
| **Date** | 2026-08-05 |
| **Context** | The sandbox runs against a local HuggingFace TGI 3.0 endpoint (`system_fingerprint: 3.0.0-sha-8f326c9`) serving `llama-3.1-8b-instruct`, which is the only LLM this track is permitted to use. | **Options Considered** | (A) Patch each call site as it breaks — smallest immediate change, but the divergence is per-request rather than per-caller, so it recurs once per agent and every future agent inherits the bug. · (B) Subclass `ChatOpenAI` and override the response-parsing methods — fixes all consumers of that class, but couples this project to `langchain-openai` internals that `Bugs.md` #4 and `Research.md` topic 10 already establish are moving quickly. · (C) An `httpx.HTTPTransport` subclass rewriting request and response bodies in transit, installed once on the shared client. · (D) Change servers, or run a proxy in front of TGI — clean separation, but the local endpoint is a fixed constraint and a proxy adds a process to operate. |
| **Chosen Solution** | (C). |
| **Rationale** | The mismatch is at the protocol layer, so the fix belongs at the protocol boundary — below every consumer, above the server, and coupled only to the HTTP shape both sides already agree to document. It required no change to any agent, supervisor, or tool, and it is the one place where a passing test genuinely covers all five workers at once. It also degrades safely: non-`/chat/completions` paths and streaming (`text/event-stream`) responses pass through untouched, and a body that fails to parse is returned unmodified. |
| **Impact** | Directly rehearses the orchestrator's **agent adapter** layer, which is Build Guide Stage 4 and currently unwritten. Every vendor CLI will have its own equivalent of `arguments`-as-dict, and this ADR fixes where that gets absorbed: in the adapter, once per vendor, never in the router or the workflow code that reads its output. Two constraints carry forward. The shim is **vendor-specific and unconditional** — it is installed for the `custom` provider regardless of what is actually behind the endpoint, which is acceptable for one known server and is not a model for a multi-vendor adapter registry, where capability should be detected or configured rather than assumed. And it is **silent by design**: it rewrites bytes without logging, so a future server that stops needing it will not announce that fact. Related, and part of what made the choice easy: `STRUCTURED_OUTPUT_METHOD = "function_calling"` in `config.py` (`Bugs.md` #8) handles a *capability* gap in the same server, and deliberately lives in configuration rather than in the shim, because it is a negotiable client choice rather than a wire-format defect. |

## ADR-011 · Guarantee agent-loop termination in code; treat prompt instructions as advisory

| Field | Detail |
|---|---|
| **Decision** | Bound every worker agent and every supervisor with explicit structural caps — `TOOL_CALL_RUN_LIMIT` on tool calls per worker invocation, `MAX_WORKER_REPORTS` on how many times a supervisor may route to the same worker — and treat prompt wording as something that may help a stronger model but is never what makes a run terminate. |
| **Date** | 2026-08-05 |
| **Context** | Recorded after four consecutive non-terminating runs, each fixed only to reveal the next. `Bugs.md` #9 established by controlled A/B against the live server that `llama-3.1-8b-instruct` on TGI is grammar-constrained to emit a tool call on every turn while tools are attached: the identical conversation returns another tool call with empty content when `tools` is present, and a complete finished answer as ordinary text when it is absent. The ReAct exit condition — an assistant turn with content and no tool calls — is therefore unreachable, and this is a property of the serving stack rather than a defect in the agent code. Two prompt-level remedies were tried and **observed to fail**: an explicit `finish_work` tool with a "call this when the work is complete" instruction produced another `write_document` call, and a `scope` sentence telling a supervisor which parts of a request its team cannot perform was ignored by the router, which re-selected the same worker anyway (`Bugs.md` #13). |
| **Options Considered** | (A) Improve the prompts — the intuitive fix, and the one actually attempted first at both layers; empirically it does not work with this model, at either layer. · (B) Give the model an explicit termination tool — tested directly, and it called the work tool instead. · (C) Use a larger model — the real fix for output quality, but unavailable: the local endpoint is a fixed constraint on this track, and it would leave termination dependent on model behaviour rather than guaranteed. · (D) Cap the loop structurally in code, at both the worker layer (`ToolCallLimitMiddleware(run_limit=…, exit_behavior="end")`) and the supervisor layer (count prior reports per worker, force `END`), with the caps and their reasoning in `config.py`. |
| **Chosen Solution** | (D), with (A)'s prompts kept in `prompts.py` and documented in-code as not being the mechanism. |
| **Rationale** | Termination is a safety property, and a safety property cannot rest on the cooperation of the component it constrains. The A/B evidence is decisive rather than suggestive — the model does not *choose* to keep calling tools, it is prevented from doing anything else — so no amount of instruction could have closed it. Retaining the prompts costs nothing and they are correct statements about each team's remit; they are simply not load-bearing. A third piece was needed to make (D) work at all: `agent_report()`, because the middleware's terminal message is a bookkeeping stub that the supervisor reads as unfinished work, which relocated the loop one level up rather than ending it. |
| **Impact** | This is the same argument as the project's **deterministic check runner**, reached from the model side rather than the verification side, and it strengthens ADR-004's constraint that Maestro's own completion signals stay subordinate to exit-code checks: here is a first-hand case where an agent could not signal completion even in principle. Two costs are accepted knowingly rather than discovered later. The caps **change behaviour, not just safety** — `Bugs.md` #15 records a full pipeline run that terminated cleanly and produced nothing, because the top-level cap fired before the writing team was ever reached; a bound that can abandon a task must record *why* it stopped, and the current implementation logs the same `forcing FINISH` line for "no more work" and "gave up". And `agent_report()` counts *requested* tool calls including the one the cap blocked, so it over-reports by one — tolerable as a supervisor hint, wrong as an audit record, and a conflation the orchestrator's event log cannot inherit. For Build Guide Stage 4 onward this ADR argues that per-step attempt caps and fix-loop bounds — already named as non-optional in `Architecture.md`'s 2026-08-03 changelog — are termination *design*, not defensive extras, and that `recursion_limit`-style backstops (`Bugs.md` #12) do not substitute, since reaching one is always a lost run. |
| **Status (2026-08-06)** | **Widened from termination to constraint in general, and one of its two accepted costs is repaid.** Three more prompt-level rules were observed to lose to something concrete in the model's context, which puts this ADR's claim on a broader footing than loop termination: the note taker aimed its outline at the deliverable because the *request* named that file and the system prompt merely forbade it (`Bugs.md` #20); `doc_writer` kept issuing a second whole-file write despite an explicit instruction not to; and Claude Code wrote its chart into its own scratchpad because *its* system prompt named an absolute path where the role brief said "the workspace directory" (`Bugs.md` #22). The pattern is sharper than "prompts are advisory": **a rule loses to a fact**, so a constraint must be enforced where the fact lives. Three enforcement points were added, in order of how reliably they hold — `single_call_limit(tool_name)` (middleware, `run_limit=1` on `write_document` and `create_outline`, since both replace the whole file and the last call is reliably the thinnest); refusal *inside* the tool with a self-correcting error naming the alternative; and the tool's **return value** as an instruction channel (`"Document saved to: X (1459 chars). The document is complete. Do not call write_document again."`), which an 8B model heeds where the same sentence in a system prompt did not — a tool result is recent, specific, and about work just performed. Separately, the cost this ADR recorded as accepted — that `agent_report()` conflated *attempted* with *executed* — is now **repaid in the report body**: it appends a `Tools executed:` line drawn from the transcript, so a worker's prose claim and the calls it actually made are separable, which the supervisor's new EVIDENCE RULE routes on. The other accepted cost stands unchanged: a bound still logs one line for "stopped because done" and "stopped because bounded". |

## ADR-016 · Bound a worker turn by wall-clock on a daemon thread, and let a failed worker report instead of raising

| Field | Detail |
|---|---|
| **Decision** | Route every worker invocation through `run_worker(agent, name, state)`, which enforces `WORKER_DEADLINE_SECONDS = 180` of **wall-clock** time over the whole turn using `run_with_deadline()` — a **daemon** thread — and which converts a deadline miss or any exception into a **report the supervisor can route on**, never an exception that leaves the graph. |
| **Date** | 2026-08-06 |
| **Context** | Three failures with one shape, all found in a single afternoon of runs (`Bugs.md` #17, #18, #19). `LLM_RESPONSE_TIMEOUT_SECONDS = 150` was set and could not fire: it is a per-read timeout, and a server that holds the socket open while it generates never trips it — one turn ran **388 s** and ended on the server's own 500 rather than on any limit of ours. It was also not reaching workers at all, because `create_agent` calls the model directly and never passes through `llm/invoker.py`, so the effective value was the OpenAI SDK's 600 s default. The same gap meant the invoker's entire error taxonomy was inapplicable to worker turns, and one 422 aborted a run that had already produced a completed research report and a 1,459-character document. And the escape mechanism itself had a defect: `_invoke_once` used a `ThreadPoolExecutor` context manager whose `__exit__` calls `shutdown(wait=True)`, so it blocked on the exact call the timeout existed to escape. |
| **Options Considered** | (A) Raise the per-read timeout — does nothing, since the quantity is wrong rather than too small. · (B) Run each worker in a **subprocess** so it can be killed outright — the only option that truly reclaims the resource, but it forces the whole graph state across a process boundary for a sandbox, and LangGraph objects are not built for it. · (C) `ThreadPoolExecutor` with `shutdown(wait=False, cancel_futures=True)` — the obvious fix, and **wrong**: `concurrent.futures` registers an `atexit` hook that joins its non-daemon threads, so an abandoned call kept the interpreter alive after the run had printed its summary (`Bugs.md` #18, reproduced in five lines). · (D) A daemon thread with `Thread.join(timeout)`, abandoning the call if it overruns, plus a `try/except` at the same choke point that returns a report. |
| **Chosen Solution** | (D). |
| **Rationale** | Nothing in CPython can cancel a thread blocked on a socket read, so the only question available is whether that thread outlives the process — and a daemon thread's answer is no, which is what (C) got wrong by name rather than by intent. The cost is chosen deliberately and stated in the code: one idle thread and one server slot until the response finally lands, which is strictly cheaper than paying the deadline twice by waiting for it. Wall-clock is the right unit because it is the only one that bounds *the thing being paid for* — a turn's model calls and tool calls together — where a socket-level timeout bounds silence, which is not the failure. On the reporting half, the argument is the one that generalizes furthest: **a supervisor can route around a worker that failed; it cannot route around a traceback.** Converting the exception is not swallowing it — the full traceback still goes to the log at ERROR, the report is truncated to 300 characters because a provider error quotes the entire rejected generation, and the report states what survives ("anything it saved before failing is still on disk"), which is the fact the next decision depends on. Putting it at one choke point rather than in five nodes is ADR-010's argument again. |
| **Impact** | `DeadlineExceededError` is deliberately a new exception type rather than the builtin `TimeoutError`, documented as "never raised by a provider, so catching it cannot swallow a real transport timeout" — the distinction matters because this codebase now has two timeout meanings in play. `contextvars.copy_context()` carries the run's correlation id into the thread, without which tool logs from an abandoned turn lose their id exactly when it is most needed (ADR-013 status). Both timeout paths share the one helper, and `LLM_RESPONSE_TIMEOUT_SECONDS` is now applied on the client as well as in the invoker, since a limit enforced on one of two routes to a resource is not enforced. For the orchestrator this fixes three properties of the agent adapter contract. A limit must **name its unit** — `maestro delegate --timeout` is documented as a stale-stream timeout, i.e. the same blind spot in the tool this project delegates through, so a wall-clock deadline over the subprocess is required regardless. An adapter **returns a classified outcome and never raises past the router**, or one vendor's bad generation costs every worktree in flight. And a bound must say **what state it leaves behind**, because unlike an LLM call, an abandoned agent turn is not idempotent — which is ADR-005's premise arriving from the timeout side. `claude_agents/cli.py` already implements the same contract over a subprocess (`ClaudeResult` mirrors `LLMResult` and never raises), and a subprocess is the case where option (B)'s real kill becomes available again. |

Remove disabled reviewer/supervisor nodes from the graph rather than bypassing them. |
| **Date** | 2026-08-07 |
| **Context** | The temporary pipeline diagram and ChatGPT/Claude research converged on six responsibilities, but the drawing alone did not specify wave repetition, loop bounds, or how optional gates should affect topology. The implementation needed resumable state, interrupts for user clarification, and explicit backward routes without scattering configuration checks through every router. |
| **Options Considered** | A straight single-pass script; Maestro as the entire controller; one large orchestration agent; a LangGraph state machine with explicit stages and semantic routes. |
| **Chosen Solution** | Compile a LangGraph whose routers return semantic keys and whose edge maps translate those keys to the enabled topology. Bound review at two rework rounds per wave and supervision at one replan per run. Record guard exhaustion as `bounded`, not `completed`. |
| **Rationale** | The graph makes pauses, resumes, loops, and terminal states inspectable. Semantic routes keep toggles in one place. Removing a disabled node means it cannot incur cost, appear in the log, or be reached accidentally. The two loops represent different judgments: reviewer findings concern implementation of a wave; supervisor findings may invalidate the plan itself. |
| **Impact** | `orchestrator/graph.py`, `routes.py`, and `state.py` own topology and termination. Reviewer and supervisor are configurable quality gates. Only judgment stages can send the pipeline backward. |

## ADR-018 · Derive waves deterministically and treat each wave as reversible Git integration

| Field | Detail |
|---|---|
| **Decision** | Let the planner define tasks and dependency edges, derive dependency waves in code, branch every same-wave task from one base SHA, merge successful task branches provisionally, and reset integration to that base when a wave is rejected. |
| **Date** | 2026-08-07 |
| **Context** | Research showed that asking a model to put independent tasks in the same wave produces plausible schedules whose errors are silent. Parallel tasks also cease to be independent if their worktrees start from different commits. Review must be able to reject integrated work without destroying task evidence or the coding sessions needed for rework. |
| **Options Considered** | Model-generated wave numbers; serial execution in one checkout; permanent merge on first success; isolated worktrees with code-derived waves and reversible integration. |
| **Chosen Solution** | Normalize planner dependencies, validate dangling references and cycles, derive waves with Kahn's algorithm, create a task worktree/branch for each task from the same integration SHA, merge sequentially into a provisional integration branch, and rewind on rework or replan while retaining task branches and session ids. |
| **Rationale** | Task decomposition is judgment; topological scheduling is arithmetic. Git supplies the transaction boundary and observable evidence. Rewinding integration preserves correctness while retained branches and session ids preserve inspectability and continuity. |
| **Impact** | Implemented in `planner/waves.py`, `wave_orchestrator/`, `worktrees.py`, and `merger/`. Same-wave tasks can run concurrently without seeing one another's partial work. Rework and replan have distinct reset points. |

## ADR-019 · Normalize every agent backend behind a closed, non-raising adapter contract

| Field | Detail |
|---|---|
| **Decision** | Make direct Claude, direct Codex, Maestro delegation, and the scripted stub implement one request/result contract. Adapter calls return classified failures and never let a worker traceback escape into graph routing. |
| **Date** | 2026-08-07 |
| **Context** | The August 6 CLI experiments showed that vendor runtimes differ in prompt transport, final-answer channels, session telemetry, error placement, permissions, model entitlement, and timeout behavior. Maestro adds lifecycle features but its timeout is stale-stream based rather than a wall-clock bound. |
| **Options Considered** | Vendor-specific calls inside each node; Maestro-only invocation; a common adapter interface with transport-specific normalization; exceptions as the common error path. |
| **Chosen Solution** | Define `AgentRequest` and `AgentResult` in `adapters/base.py`, keep a closed error taxonomy, place wall-clock deadlines around subprocesses, preserve vendor telemetry when available, and select direct, Maestro, or stub transport through configuration. |
| **Rationale** | A supervisor can route around a worker that failed; it cannot route around a traceback. A closed taxonomy lets routers match exhaustively without parsing prose. Keeping transport separate from vendor preserves direct control while allowing Maestro's lifecycle when desired. |
| **Impact** | Nodes call one stable boundary. Claude can resume sessions and report cost; Codex uses a designated output file; Maestro resolves the repo-local executable and runs synchronously; tests use a first-class stub that fails when a step was not scripted. |

## ADR-020 · Make durable artifacts and observable repository state the source of continuity and acceptance

| Field | Detail |
|---|---|
| **Decision** | Persist requirements, explicit user choices, plans, task contracts, events, learnings, reviews, checkpoints, and logs outside the target repository. Treat agent reports as claims and Git/filesystem observations as evidence. |
| **Date** | 2026-08-07 |
| **Context** | Earlier sandbox runs ended cleanly while producing nothing, agents reported files they could not write, and a merge reviewer approved bytes it could not see. Requirements clarification also needed to survive LangGraph interrupts without paying for the survey twice or asking a model to avoid inventing user choices. |
| **Options Considered** | Conversation-only state; one model-written summary; artifacts inside the target checkout; orchestrator-owned artifacts plus SQLite checkpoints and repository evidence. |
| **Chosen Solution** | Store one run under `orchestrator/runs/<run-id>/`, checkpoints under `orchestrator/checkpoints/`, and logs under `orchestrator/run_logs/`. Split requirements survey from clarification, record Q&A verbatim in `user_choices.md`, compare claimed files to Git diffs, and verify conflict resolution through both Git and marker scans. |
| **Rationale** | Durable entry-time reconstruction survives agents, vendors, checkouts, and process restarts. Orchestrator-owned Q&A cannot add assumptions the user never made. Acceptance based on observable state closes the plausible-empty-result failure class. |
| **Impact** | Runs are auditable and resumable by id. Artifact writes are immediate; events and learnings are append-only. Review and supervision receive both claims and evidence. |
