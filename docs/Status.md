#### 2026-07-31 — Requirements checklist, tool survey, and initial architecture decisions

* Set out to find — or determine whether it's necessary to build — an open-source, locally deployable platform that dynamically orchestrates existing coding-agent CLIs (Claude Code, Codex, Gemini CLI, others) through planner → implementer → reviewer → fixer workflows with a shared, canonical task context across handoffs.
* Diagnosed: no single surveyed tool (10 frameworks, plus Command Code and OpenHands Agent Canvas) fully satisfies the requirements checklist. #### 2026-08-03 — Maestro chosen as the execution layer; handoff and budget mechanics pinned down

* Set out to settle ADR-003's open two-way choice between Claw Orchestrator and OpenHands Agent Canvas by working with them directly instead of comparing feature lists.
* Diagnosed: the two are not really competing on the same axis. Claw's abstraction is a coordinated *group* of external agent sessions (Council, fan-out, worktree-backed parallelism); OpenHands' is a complete *environment* for running dev agents (sandboxes, UI, secrets, ACP, deployment backends). Neither implements token-aware cross-agent failover, so the core custom work is identical either way — and if the orchestration logic lives in a separate layer, Claw's coordination primitives go unused and its advantage collapses. Also corrected an earlier misreading: OpenHands *does* provide persistent conversations and multi-engine access via ACP (`Research.md` topic 5).
* Attempted a hands-on OpenHands trial against a self-hosted OpenAI-compatible LLM endpoint, with a first task chosen to exercise file creation plus deterministic verification without needing the rest of the stack running. It never reached agent execution — every request failed with `litellm.InternalServerError: OpenAIException - Connection error.` Cause not isolated; the trial was dropped when the execution layer moved to Maestro the same day (`Bugs.md` #1).
* Reviewed **Temporal** as the durable-workflow option alongside the Langflow/LangGraph question. Flagged that the provisional stack table said Langflow while ADR-002 had chosen LangGraph — these are different tools, and Langflow is a visual builder rather than a durable state-machine runtime, so it is ruled out as the engine. Detailed Temporal evaluation notes were not captured in the session transcripts and are still owed to `Research.md` topic 7.
* Learned about **Maestro-flow (Ralph)** and **Flow-next**, and found that both already do mid-task delegation to a *different* coding-agent CLI — the exact primitive the earlier 10-tool survey concluded was missing everywhere. Ralph's `cli` node type routes a chain step through `maestro delegate` as a background delegate execution; Flow-next exposes `plan-review` and `impl-review` as named commands with a swappable review backend. Ralph's decision gates are all post-execution, so a pre-execution plan-review checkpoint needs hand-assembly; Flow-next covers that natively (`Research.md` topic 8).
* **Decided: use Maestro** (ADR-004) — chosen for its general-purpose `delegate` primitive, Session/Run lifecycle, and knowledge system, and because it is already installed and configured here. Flow-next is the more configurable of the two out of the box and is retained as the fallback. This withdraws Claw Orchestrator from ADR-002 and resolves ADR-003 in the negative for both of its candidates.
* Also decided two mechanics that everything else rests on: handoff packets are **reconstructed on entry** from continuously-written durable artifacts rather than summarized on exit (ADR-005) — the naive summarize-on-exit design fails precisely when an agent is killed by a rate limit, which is the case the whole feature exists for. And agent budgets are modelled as a **configured ledger with reactive limit detection as the authoritative signal** (ADR-006), because no target agent exposes remaining allowance and the four are not bounded by comparable quantities.
* Environment work: installed Claude Code v2.1.220 and fixed its PATH (`Bugs.md` #2); created a project virtualenv on **Python 3.13.13** via `uv`, moving off the locally installed 3.14 because the agent/LLM package ecosystem lags new interpreter releases and several intended dependencies ship compiled wheels.
* No code was written this session. Build guidance and a phase-scoped dependency list were produced during the session but **were not saved into the repository** — `docs/Build-Guide.md`, `requirements.txt`, and `requirements-dev.txt` do not exist in the working tree or in git history. Their substance is preserved in ADR-005, ADR-006, `Research.md` topics 6–8, and the `Architecture.md` changelog; the phased build order and the concrete v0 acceptance test are **not** yet recorded anywhere and should be rewritten before implementation starts.
* Target for v0, worth restating since it is the clearest definition of done: give the system a real task in a real repo, set one agent's budget artificially low so it will be exhausted partway through, and have the system plan, start implementing, detect the limit, fail over to a second agent mid-task, continue from the existing partial work rather than restarting, pass the deterministic check runner, and leave a complete audit trail.
* Tracked in: `docs/Decisions.md` (ADR-004, ADR-005, ADR-006; status updates on ADR-002 and ADR-003), `docs/Research.md` (topics 5–8), `docs/Architecture.md` (stack table, Agent Router, Handoff Builder, changelog entry), `docs/Bugs.md` (entries 1–2).

#### 2026-08-05 — The tutorial hierarchy completed and made to run; nine defects found by execution; the sandbox reorganized into packages with config, prompts, and per-run logging

* Set out to finish the hierarchical multi-agent build started the previous session — the writing team, the top-level orchestrator over both teams, and a first real invocation — then, once it ran, to reorganize it into something readable and to wire up the logging module that had been sitting unused. Two commits: `258e04e` *Tutorial code completed* and `5e4fb11` *Organized, cleaned, logging added, config added*.
* **Completed the hierarchy.** `writing_team.py` (three workers: `doc_writer` over write/edit/read, `note_taker` over outline/read, `chart_generator` over read plus a Python REPL, and their supervisor), `writing_builder.py`, and `super_builder.py` — the top-level graph routing between `research_team` and `writing_team`, each a compiled sub-graph invoked from a node. `main.py` streamed the first real request through it. Both teams reuse the same `make_supervisor_node` factory, which is the piece the whole exercise was for.
* **Both latent defects fired, and reading had missed a third.** `Bugs.md` #5 raised its predicted `TypeError: 'LLMResult' object is not subscriptable` on the first invocation; fixed with a `Router` TypedDict bound through `.with_structured_output(...)`, passed *through* `llm_invoke` so the supervisor keeps the FIFO gate, plus the `result.ok` check the original entry had also flagged. The third defect surfaced only while fixing it: `State` had no `next` key, so the supervisor's `update={"next": goto}` had **always been a no-op** — LangGraph silently discards updates to channels absent from the schema, verified with a minimal two-node graph. An unknown edge target is a compile-time error; an unknown state key is not an error at all. `Bugs.md` #6 fired too, and exactly as silently as its own Symptom field predicted (below).
* **Diagnosed the local serving stack by probing it rather than trusting "OpenAI-compatible."** The endpoint is HuggingFace TGI `3.0.0-sha-8f326c9` serving `llama-3.1-8b-instruct`. A capability probe found plain chat 200, `response_format` json_object **500**, json_schema **500**, tool calling 200 — and json_schema is what `langchain-openai` 1.4.1 sends by default from `with_structured_output()`, so the library's default was the one route the server does not implement (`Bugs.md` #8; fixed with `STRUCTURED_OUTPUT_METHOD = "function_calling"` in config). Four further deviations sit in the wire format itself: `arguments` returned as a JSON object rather than a string, `content` omitted on tool-call turns, every tool call labelled `id: "0"`, and — bisected with five message shapes differing only in that field — HTTP **500** for any assistant message with `content: null`, which is exactly what langchain re-serializes an empty content field into on the next turn (`Bugs.md` #7).
* **Wrote `tgi_compat.py`, a 142-line `httpx` transport shim** normalizing all of it in both directions, and put it on the transport rather than in the agents (ADR-010). The first fix attempt patched the supervisor and would have left all five workers broken one turn later, which is the argument in miniature: the divergence is per-request, not per-caller. Verified by A/B on an identical payload against the live server — default transport 500, compat transport 200 — and against a stub reproducing TGI's exact captured bytes.
* **Established that the loop could not be closed by prompting.** A controlled A/B sent the same conversation twice, differing only in whether `tools` was in the request: with tools, another tool call and empty content; without, a complete finished answer as text. TGI grammar-constrains generation to the attached schemas, so while tools are bound the model **structurally cannot** produce the assistant-turn-with-content-and-no-tool-calls a ReAct loop exits on. An explicit `finish_work` tool was tried and the model called `write_document` instead. Bounded it with `ToolCallLimitMiddleware(run_limit=3, exit_behavior="end")` — and the loop **moved** rather than closing, because the middleware's terminal stub (`Tool call limit reached: …`) was being handed to the supervisor as the worker's report, where it reads as unfinished work. `agent_report()` now replaces that stub with what the worker actually did (`Bugs.md` #9, ADR-011).
* **Then the same pattern one level up.** The research team looped on a request asking it to "compile in a file named `research_results.txt`" — it has no file-writing tool, its search worker satisfied the first clause on pass one, and the supervisor re-routed forever chasing a clause it structurally could not complete. Adding a `scope` sentence to the supervisor prompt telling it so **did not work**; the 8B router ignored it. A structural repeat cap (`MAX_WORKER_REPORTS`) did. The scope prompts were kept because they are correct and should help a stronger model, and documented in-code as not being the mechanism (`Bugs.md` #13).
* **Fixed a sandbox escape that was also the engine of a rewrite loop.** The document tools built paths as `os.path.join(cwd, "temp", file_name)` and returned the **absolute** path; `os.path.join` discards its base when the tail is absolute, so the tool announced a path, the model echoed it back as `file_name`, and the resolver honoured it — a perfect fixed point, and a write-anywhere-on-disk hole in the same line. Now `basename`-sandboxed, returning bare filenames (`Bugs.md` #10).
* **Three more tool-layer defects that only execution could surface** (`Bugs.md` #11): `python_repl_tool` referenced an undefined `repl` and its own `except Exception` had been converting the resulting `NameError` into a returned string, so the tool had never worked and had never looked broken; bare `open()` on Windows defaults to cp1252 and died on an em dash in model output (`UnicodeEncodeError: 'charmap' codec…`) *after* a correct tool call; and `read_document`/`edit_document` raised on a missing file, so one hallucinated filename killed an entire graph run, while `python_repl_tool` in the same file returned its errors as text. All four file operations are now `encoding="utf-8"`, and the document tools report errors with a listing of what is actually in the workspace so the agent can self-correct.
* **`recursion_limit` is a step budget, not a nesting depth, and sub-graphs inherit it.** `{"recursion_limit": 2}` at the entry point surfaced as `GraphRecursionError` raised *inside* `research_graph.invoke()`, which had been called with no config of its own — the level that exhausts a shared budget is not the level that misconfigured it. Fixed with explicit per-level allocation (`SUPER_GRAPH_RECURSION_LIMIT = 50`, `TEAM_CONFIG` at 25). The same call site was also passing a single message where a list is contracted; `add_messages` had been coercing it, which made it work by accident (`Bugs.md` #12).
* **Reorganized the sandbox into packages** (ADR-012): `llm/` (`clients.py`, `invoker.py`, `tgi_compat.py`), `tools/` (`documents.py`, `web.py`, `code.py`), `teams/` (`state.py`, `supervisor.py`, `research.py`, `writing.py`, `orchestrator.py`, `visualization.py`) over `main.py`, `config.py`, and `prompts.py`. Six modules collapsed — each `*_builder.py` merged into its team module, `state.py` split into pure state and the supervisor factory. `config.py` grew from 20 to 83 lines and became the single source of tunables, each non-obvious constant carrying *why* it holds that value, because several of them are the findings above: `TOOL_CALL_RUN_LIMIT = 3`, `MAX_WORKER_REPORTS = 2`, `STRUCTURED_OUTPUT_METHOD = "function_calling"`, and `LLM_MAX_RETRIES = 0` (the invoker owns retry policy; an SDK retrying underneath would hide the 429s its FIFO gate exists to handle). Prompts went to a separate module because they change for different reasons than tuning constants. Behaviour was held fixed: both team graphs were re-run and routed identically, and a supervisor's fully assembled prompt was reconstructed after the extraction and compared byte-for-byte.
* **The ported `logger_config.py` turned out never to have executed.** Its first real call raised `NameError: name 'tracing_handler' is not defined` — two handler variables were referenced and never constructed, neither constructible here since `langfuse` and `openinference` are absent, and about half the file imported `app_workflow.*` packages belonging to `RAG-work`. Undetected for a day because nothing imported it. Replaced rather than repaired, 265 lines in and 132 out, keeping the `ContextVar` request-id filter, the dual console/file handlers, and the muted-library list (`Bugs.md` #14, ADR-013). This is deliberately the opposite call to ADR-009's port-as-is, and the distinction that emerged is: **port what is expensive to re-derive, rewrite what is cheap.**
* **Instrumented the pipeline and got one `run_logs/<app>_<timestamp>.debug.log` per run** — console at INFO, file at DEBUG, every supervisor decision, worker entry and report, team entry and exit, and every tool operation with sizes. It paid for itself immediately, and produced the session's most important finding.
* **The full pipeline now runs end to end and terminates cleanly — and its most recent complete run produced nothing.** `agent_run_20260805_163729.debug.log`: five steps, no exception, exit 0, `FINISH`, and `Run finished | steps=5 | documents=none` against a request that asked for a file. So the guard introduced to bound a loop also acquired the power to abandon a task, logging the same line for both. Every completion signal the system emits about itself agreed, and all of them were wrong; only comparing artefacts against the request revealed it.

Both halves of the ledger analogue are inert, silently, and the runs look entirely normal (`Bugs.md` #6a).
