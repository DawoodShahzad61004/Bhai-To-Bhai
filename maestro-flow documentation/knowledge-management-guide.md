---
title: "Knowledge Consolidation Management System"
---

Maestro's knowledge consolidation comes in two forms: **constraints** and **accumulation**. Constraints are coding conventions, architectural decisions, and quality rules — they define "what must not be done." Accumulation is operating procedures, design assets, and debugging experience — it records "how it was done." The former must be force-loaded; the latter is retrieved on demand.

> For the authoritative system design, see [Maestro Knowledge System Architecture](../docs/knowledge-system-architecture.md). This document focuses on day-to-day operations; the identity model, Run ledger, reconciliation freshness, retrieval diversity, and safe pruning are governed by the architecture document.

## The Relationship Between Spec and Knowhow

**Spec is the index and the rules; Knowhow is the detail and the process.** The two are bridged by the `ref` attribute.

| Layer | Role | Content Characteristics | Loading Method |
|---|---|---|---|
| Spec (`specs/`) | Index + rules | Short entries, summaries under 200 words | Auto-injected (hook) |
| Knowhow (`knowhow/`) | Detail documents | Full steps, code examples | Loaded on demand (`wiki load`) |

### The Session/Run Knowledge Review Loop

A Run no longer writes conclusions straight into Spec/Knowhow; it goes through a reviewable two-phase process:

```text
[auto] search/load → automatically recorded as consumed
[auto] check → automatic reconcile
[auto] complete → automatically stages decisions/constraints
[manual] review → review + adjudication
[manual] promote → explicit promotion
[manual] seal → close out
```

```bash
# Stage a candidate (optional; decisions/constraints are staged automatically on complete)
# For long bodies, use --content-file <path|-> instead
# --signal/--signal-ids can also record Run relationships such as validated/contradicted
maestro knowledge stage spec "Rule title" "Rule body" \
  --action propose --run <run-id> --session <session-id> \
  --signal validated --signal-ids spec:S-1,knowhow:K-1

# Review (--refresh includes a reconcile)
maestro knowledge review <session-id> --refresh

# Make an evidence-backed ruling on a review_required candidate (refreshes the view as part of the call)
maestro knowledge review <session-id> \
  --resolve <candidate-id> --as related --target <knowledge-id> --reason "<reason>"

# After the Run is sealed, explicitly promote the selected candidates
maestro knowledge promote <session-id> --candidate <candidate-id>
maestro knowledge promote <session-id> --all
maestro session seal <session-id>
```

`review` is read-only by default; `--refresh` includes a reconcile and should only be used when the display shows `missing` or `stale`. `--resolve` makes the ruling from inside the review interface, with no separate command needed. Search and automatic injection are only exposure; an explicit `load` is recorded automatically as consumed, and neither triggers promotion.

## The Knowledge Lifecycle

### Stable Identity (sid)

Every `<spec-entry>` is automatically assigned a stable ID on creation (format `S-YYYYMMDD-xxxx`), used for cross-file references and evolution-chain tracking. Existing entries can be backfilled with `maestro spec backfill-sid`.

### Evolution Chains (Supersession)

When new knowledge replaces old knowledge, use supersede to establish an evolution chain:

```bash
# 1. Add the new entry (the sid is generated automatically)
maestro spec add coding "New rule" "Content" --keywords kw1,kw2 --json
# The output includes the sid, e.g. S-20260704-a1b2

# 2. Mark the old entry as deprecated
maestro spec supersede <old-sid> --by <new-sid>

# 3. View the evolution chain
maestro spec history <sid>
# ○ deprecated  S-20260101-x1y2  "Old rule"
#     ↓
# ● CURRENT     S-20260704-a1b2  "New rule"
```

Superseded entries automatically get `status="deprecated"` and are excluded from search and agent injection, but remain viewable via `--include-deprecated`.

### Two Tracks for Conflicts

The relationship between new knowledge and an existing entry falls into two categories with different semantics and different operations:

| Relationship | Scenario | Operation | Old Entry Status |
|------|------|------|-----------|
| **supersede** | The new rule replaces the old rule (evolution) | `maestro spec supersede` | `deprecated` (excluded) |
| **conflict** | Both rules have merit (contested) | `maestro spec conflict mark` | `contested` (down-weighted but retained) |

### Health Check

```bash
maestro spec health
```

Output: lifecycle statistics (active/deprecated/contested), the number of evolution chains, detection of dangling/circular supersedes, and the overall mean freshness.

## Tool — Executable Knowledge

A Tool is a knowhow document marked with `tool: true` that defines an **executable business process** — a lightweight workflow that lives in the project directory and is self-discovering and self-applying.

```yaml
---
title: Payment Gateway Idempotency Verification
type: recipe
category: test
keywords: [payment, gateway, idempotency]
tool: true
summary: "Use when testing payment endpoints for retry safety."
---

## Steps
1. Generate idempotency key (UUID v4)
2. Submit charge request with key
3. Retry same request — assert identical response
4. Submit different amount with same key — assert 409
5. Verify webhook delivers exactly once
```

`maestro spec load --category test` automatically scans knowhow/ for documents with `category=test` and `tool=true`, and injects the tool summaries into the agent context alongside the specs.

### Registration and Use

A Tool is simply a knowhow document with `tool: true`: consolidate it with `/maestro-knowhow` (recipe type + `--tool`), and agents discover it automatically through `maestro spec load --category` and get the summary injected — no dedicated registration or execution command is required.

## Code Knowledge Graph Integration (KG × Wiki)

Once `maestro kg index` has generated `knowledge-graph.json`, WikiIndexer automatically indexes the KG data as virtual wiki entries:

| KG Data | Wiki Entry | virtualKind | Purpose |
|---------|-----------|-------------|------|
| GraphNode | `kg-{id}` | `kg-node` | Code entities (functions, classes, modules) |
| Layer | `kg-layer-{id}` | `kg-layer` | Architecture layers (CLI, Core, Orchestration) |
| TourStep | `kg-tour-{order}` | `kg-tour-step` | Code tour steps (chained as a linked list) |

**Two-tier edge storage**: `related[]` holds the top-N related IDs (used for wiki graph analysis), while `ext.kgEdges[]` holds the full directed heterogeneous edges (used for semantic traversal).

**Search down-weighting**: KG nodes index only title + tags in BM25, so code identifiers do not pollute regular search.

**Cross-references**: KG nodes are automatically matched to `codebase-comp-*` entries via `filePath`, establishing an `ext.semanticDuplicateOf` reference.

```bash
# View the KG index
maestro wiki list --keyword kg

# Search for code entities
maestro wiki search "AuthMiddleware"

# Code change impact analysis
maestro kg diff-wiki

# KG node details (including linked wiki entries)
maestro kg explain <node-id>
```

## The Domain Knowledge System

The Domain system manages the project's domain glossary, providing domain context for spec injection and code comprehension. Its core modules are `domain-loader.ts` (term CRUD + file locking), `domain-scanner.ts` (code scanning to discover candidate terms), and `domain-matcher.ts` (CJK-aware term matching).

### CLI Subcommands

| Subcommand | Responsibility |
|--------|------|
| `domain init` | Initialize `.workflow/domain/` and an empty `glossary.yaml` |
| `domain add <canonical> <definition>` | Add a domain term (supports aliases, keywords, relationships, tier) |
| `domain list` | List all terms; supports `--status active\|deprecated` filtering |
| `domain show <id>` | View term details (including the concept_ref document content) |
| `domain update <id>` | Update a term (definition, aliases, relationships, keywords, tier) |
| `domain remove <id>` | Delete a term (checks reference dependencies, returns warnings) |
| `domain search <query>` | Search terms (canonical + aliases + definition + keywords) |
| `domain discover` | Scan the codebase for candidate terms (based on interface/type/enum/class/route/doc) |
| `domain import` | Import terms from an external source (`--from context-package \| @<file>`) |
| `domain deprecate <id>` | Soft-delete a term (marked deprecated; a successor can be specified) |
| `domain validate` | Validate the `glossary.yaml` schema and relationship integrity |

### Term Structure

Each term contains: `id` (kebab-case), `canonical` (display name), `definition`, `aliases[]`, `keywords[]`, `relationships[]`, `tier` (core/extended/peripheral), `status` (active/deprecated), `source` (manual/discover/import), and an optional `concept_ref` (path to a detailed concept document).

### Integration with Spec Injection

Before injecting spec entries, `spec-injector` and `keyword-spec-injector` first use `domain-matcher` to match domain terms in the prompt, then inject the matched term definitions as a context prefix, helping the agent understand project-specific concepts.

## The Credibility Assessment System

`credibility.ts` implements **exponential-decay**-based knowledge credibility scoring, and `spec-analytics.ts` records injection logs for improvement analysis.

### The Decay Model

```
factor = floor + (1 - floor) * e^(-λ * age_days)
λ = ln(2) / half_life
```

| Node Type | Half-life (days) | Description |
|----------|-------------|------|
| domain | 180 | Domain terms change slowly |
| spec | 60 | Constraint rules update at a moderate rate |
| knowhow | 30 | Operational knowledge decays faster |
| issue | 14 | Issue status changes frequently |
| project/roadmap/note | 90 | Generic moderate decay |

- `floor = 0.3`: the minimum credibility guarantee
- `ceiling = 1.2`: the upper bound that search hits can raise credibility to
- `warningThreshold = 0.5`: falling below this triggers a low-credibility warning

### Storage and Updates

`CredibilityStore` uses the SQLite `credibility` table, recording `search_hits`, `consumption_count`, `last_hit_at`, `last_consumed_at`, and `content_changed_at`. When content changes, the `content_hash` comparison resets the decay start point. It supports `incrementSearchHits` (batch) and `incrementConsumption` (single) for tracking usage.

### Spec Analytics

`spec-analytics.ts` records three log types into `.workflow/spec-analytics.jsonl`:

| Type | Source | Recorded Content |
|------|------|---------|
| `injection` | spec-injector / keyword-spec-injector / spec-injection-plugin | Agent type, matched category, number of injected entries, budget action, matched keywords |
| `cli` | CLI endpoints | Command name, arguments |
| `hook` | workflow hooks | Hook name, duration, result |

Statistical aggregation provides: injection hit rate by source/agent type/category, top-N keyword rankings, CLI usage frequency, and hook invocation statistics. The log file rotates automatically (5MB by default).

## The KG Custom Extractor Plugin Mechanism

`plugin-engine.ts` supports two plugin modes for extending the knowledge graph's code extraction capability, configured through `.workflow/kg/extractors.yaml`.

### The Two Plugin Modes

| Mode | Configuration | Execution | Suitable For |
|------|---------|---------|---------|
| **declarative** | `rules[]` defined in YAML | Regex/call/assignment pattern matching | Simple symbol extraction (constants, routes, decorators) |
| **script** | `.workflow/kg/extractors/*.mjs` | Dynamic import + `extract(ctx)` invocation | Complex logic (AST traversal, cross-file analysis) |

### Declarative Rule Types

- `regex`: regex matching, with `$1`-`$9` templates for extracting the name
- `call`: function call patterns (e.g. `builder.define_constant($NAME, $_)`)
- `assignment`: assignment patterns, with `module`/`class`/`any` scope filtering

### The Script Plugin API

Script plugins export an `extract(ctx)` function; `PluginContext` provides:

- `ctx.filePath` / `ctx.sourceCode` / `ctx.language`: file information
- `ctx.findAll(nodeType)`: traverse the tree-sitter AST to find nodes of a given type
- `ctx.text(startLine, endLine)`: extract source lines
- `ctx.makeSymbol(input)`: build a normalized symbol object

### Merge Strategy

Plugin extraction results are merged with the core tree-sitter results; the conflict strategy is controlled by `defaults.conflictPolicy`: `merge-metadata` (default, keeps the core symbol), `plugin-wins` (the plugin overrides), or `core-wins` (the core is retained).

## The CooldownGuard Abstraction

`cooldown-guard.ts` provides a cross-process cooldown guard, implementing throttling between child processes through a bridge file in the temp directory.

### Core API

```typescript
class CooldownGuard {
  shouldRun(sessionId): boolean   // Whether we are still inside the cooldown window
  markDone(sessionId, extra?)     // Mark as done, writing a timestamp
  timeSinceLastMs(sessionId)      // Milliseconds since the last trigger
}
```

### Preconfigured Instances

| Instance | Cooldown | Purpose |
|------|---------|------|
| `kgSyncGuard` | 30 seconds | KG sync throttling, to avoid rebuilding the index too often |
| `kgInitGuard` | 5 minutes | KG initialization throttling, to avoid repeated full scans |

Bridge files are stored in the system temp directory (`maestro-kg-sync-{sessionId}.json` / `maestro-kg-init-{sessionId}.json`) and contain a `last_trigger` timestamp. `shouldRun()` compares the current time with the last trigger time and returns `true` once the cooldown window has passed.

## The Script Plugins Security Policy

Script plugins (`.mjs` files) are **disabled** by default and must be explicitly enabled, to prevent execution of untrusted code.

### How to Enable

```bash
# Enable explicitly from the CLI
maestro kg sync --allow-extractor-scripts

# Pass it through the code-extractor call chain
codeExtractor.extract({ allowScripts: true })
```

### Security Behavior

| Scenario | Behavior |
|------|------|
| `.mjs` files exist but scripts are not enabled | A warning is written to stderr and all script plugins are skipped |
| Enabled | Loaded via dynamic `import()`; if `extract()` fails, handling follows the `onError` policy |
| Plugin has no `export function extract` | Silently skipped |
| Declarative plugins | Always loaded; not subject to this security policy |

`warn` (default): a warning is emitted on plugin failure and execution continues. `fail`: a plugin failure throws an error and aborts the extraction.

## The Knowledge Flow Panorama

```
Execution artifacts     Extraction                        Storage           Consumption
───────────────────     ──────────                        ───────           ───────────
Analysis sessions ─┐                                  ┌─→ specs/      ─→ spec-injector    → agent
Debug records     ─┼──→ /maestro-knowledge harvest ───┼─→ knowhow/    ─→ wiki load        → on demand
Planning docs     ─┤    retrospective step            ├─→ issues/     ─→ /maestro-issue   → tracking
Code changes      ─┘    /maestro-learn decompose      └─→ learnings   ─→ keyword-injector → context
```

Progressive Fill — automatic consolidation at each stage:

```bash
maestro-init → spec init (skeleton + scan)
analyze → locked decisions → arch, code patterns → coding
plan    → design conventions → coding/arch, test strategy → test
execute → lessons learned → learning, root causes → debug
execute → built-in verification (E2.7) → quality findings → review
```

<summary>Worked example: a full-stack API development loop</summary>

Take a user management module (registration, login, JWT auth, user CRUD) as the example:

**1. Planning + analysis**

```bash
/maestro "User management module API: registration, login, JWT auth, user CRUD"
/maestro "Analyze the API endpoint design patterns"
```

**2. Implementation + knowledge harvesting**

```bash
/maestro "Implement the plan above"
/maestro-knowledge harvest --source lite-plan --to auto
```

Automatic harvest routing:

| Extracted Content | Route Target | Example |
|---|---|---|
| API naming conventions | spec → coding | "All endpoints use the `/api/v1/` prefix" |
| Auth scheme decision | spec → arch | "Passwords use bcrypt(12); tokens are signed with RS256" |
| Response format knowledge | wiki → knowhow | "Always return the `{ data, error, meta }` structure" |
| Missing functionality | issue | "No rate limiting middleware" |

**3. Test consumption**

```bash
# auto-test and test are first-tier steps dispatched by the orchestrator (maestro run), not slash commands
auto-test --keyword user-api             # Automated testing: discover the tool → generate test code
test "user management API"               # Conversational UAT: verify item by item following the tool's steps
```

**4. Feeding knowledge back**

```bash
/maestro-learn "Retrying after a refresh token expires needs to handle a race condition"
```

Responsibilities of each command:

| Command | Output | Nature |
|---|---|---|
| `/maestro-knowledge harvest` | spec entries + wiki entries + issues | Passive knowledge |
| `/maestro-knowhow` | AST-*.md (API contracts); RCP-*.md marked with `--tool` (verification procedures) | Passive asset / actively executable |
| `auto-test` step | Test code | Consumes the tool |
